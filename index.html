apprval.md human approval for agent actions

The permissions section of an AGENTS.md file is prose, and nothing checks it. approval.md is the layer that checks: a policy file a human signs for, an append-only hash-chained log, and a single-use token minted only as a decision is recorded.

npm install -g approval-md v0.1.0 · MIT · Node 20 or newer. Publishing is imminent; until it lands, clone, npm ci, npm run build, npm link.

Try the loop

The whole product in one card. An agent registered an envelope and asked; the policy resolved communicate.email.external to manual, and the irreversibility floor would have done it anyway.

How this compares

Three kinds of thing already exist here, and each solves a different part of the problem. The differentiation is the combination rather than any single feature.

  • 1Harness-native permission prompts (Claude Code rules and hooks, Cursor auto-run, Codex CLI approval modes) enforce inside the one harness they ship with, and that enforcement is real. Codex even backs its gate with an OS-level sandbox, a defense layer this project does not attempt. What they lack is a durable record and portability. This project's own Claude Code hook is built on that PreToolUse mechanism and adds the two missing pieces.
  • 2AGENTS.md permissions prose states the policy in English and trusts the agent to obey. approval.md is the enforcement layer that convention is missing, and treats it as an input: approval import agents-md reads one.
  • 3Framework interrupts (LangGraph interrupt(), CrewAI human input, AutoGen UserProxyAgent, the OpenAI Agents SDK's needsApproval, Temporal signals) give you a pause-and-resume primitive and leave policy, audit format, the human channel and the credential boundary to you. Temporal's event history deserves its credit as a genuine append-only record with crash recovery this project does not claim.
  • 4Hosted approval platforms (HumanLayer, gotoHuman, Permit.io) are the closest relatives, and they bring hosted infrastructure, escalation and team routing, and compliance certifications a file convention cannot. Their model puts a third-party service in the decision path, with the audit trail in the platform's backend.
  • 5What is different here is policy as a hash-attested markdown file in your repo, a hash-chained log you verify locally with one command, and an execution boundary where the credential is inert until a single-use token is minted at the moment a human decides. The thing the agent needs answers only to the thing it cannot make.

Global invariants

SPEC.md section 11.1 holds these across every surface of the runtime. They are implicit acceptance criteria for every task: a change that violates one is a defect regardless of what its own task asked for, and each is pinned by a named test file.

  • 1Enforcement paths read only verified records. Gate decisions are computed from log state that has passed chain verification, and a surface that cannot reach the log fails closed.
  • 2Gate-typed events never accept caller timestamps. ts is assigned by the runtime at the write boundary, and a caller-supplied value is refused.
  • 3Raw secrets never appear in the log. What appears is a hash, or ciphertext sealed to a recipient key the log does not hold.
  • 4Self-reported fields never reduce scrutiny. Values authored by the party under oversight may raise scrutiny and never lower it. Scrutiny ratchets one way.
  • 5Every check-then-append passes through compare-and-append. No path reads decision-relevant state and appends on it without the atomic head check.
  • 6Refusals are machine-readable and distinct, and every code union is pinned by a test. The unions are frozen public API.
  • 7Configuration is never loaded implicitly from the working tree. The environment a gate operation runs under is established by the human who launched the process.
  • 8A gate verdict whose event cannot be appended is a refusal. No surface returns proceed, prints an allow, or hands back a token before the record exists.
  • 9human-only classes are inert to agents. Every gate verb refuses one with the same stable code, class-human-only, and none of them appends a record on the refused path.
  • 10Guidance never reaches enforcement. The values block and the feedback reactions are human-authored guidance, and no path computing a verdict, a draw, a budget or a token reads either.

Exit codes

An agent branches on the exit code before it ever reads stdout, so these numbers are frozen. Code 1 and code 4 are kept apart deliberately: "I could not read the file" and "the file has been tampered with" are different facts about the world.

CodeMeaning
0success
1integrity failure (a corrupt log), and every gate refusal
2usage error
3torn tail
4I/O error
5no valid execution token (approval run only)
6timeout (approval wait only)

What this does not defend

Stated plainly, from SPEC.md section 11. This is an oversight layer for broadly cooperative agents, with hard enforcement at the adapter boundaries that hold the credentials. Human identity in v0.1 is config-declared, so the trust boundary is the local machine, and anyone who can set that configuration and write to the log is inside it. Attestation proves that someone with local control signed off, and never who.

An agent with direct credential access outside the adapters, a compromised host, and collusion between an agent and a careless approver are all undefended. So is persuasion about whether bytes you did see should be approved. You also run the daemon and the listener yourself, there is no OS-level sandbox, and the reference phone channel is one app. What holds regardless of what a harness believes it is running: the vault, the adapter boundary, and the single-use token.
