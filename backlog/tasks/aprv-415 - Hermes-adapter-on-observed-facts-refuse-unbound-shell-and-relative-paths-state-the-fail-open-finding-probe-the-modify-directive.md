## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The live probe of APRV-398 ran on 2026-09-21 (report in APRV-398 notes; captures in /Users/carter/dev/hermes/probe/envelopes.jsonl, 38 envelopes). Three findings change the adapter. (1) fail_closed: true did NOT block on crash, hang or garbage: all three writes happened. The source (agent/shell_hooks.py) says timeout and non-JSON stdout should block under the key, so either the installed build differs or the key was not loaded; Carter's hermes --version, hermes hooks list and the config grep decide which, and the doc must state the observed result either way. (2) The envelope cwd is the Hermes PROCESS directory (Path.cwd() in _payload_fields), while the terminal tool keeps a per-session recorded cwd that a cd moves, and all four file tools resolve RELATIVE paths against that recorded cwd (_resolve_path_for_task). The model passed no workdir on the shell call in the probe. So a terminal command without an absolute workdir, and a write_file, patch, read_file or search_files with a relative path, run against a directory the verdict cannot see: the APRV-310 shape across every tool. Fail-closed answer: refuse terminal without an absolute workdir and refuse relative paths on the file and read tools with hook-unsupported-execution-context and a reason that tells the model to retry with absolute paths, so a session stays usable. (3) Dialects confirmed: every single deny form blocks, deny-mixed blocks (Hermes tolerates supersets, unlike Muse), {} and empty stdout allow, and an invented action allow also allows (falls through). execute_code was refused before it ran, as designed. Also: Hermes documents a modify directive (action modify with args) that a shell hook may return; if honoured it would let the adapter PIN workdir to the classified directory the way the Codex adapter pins the command through updatedInput. Add a probe trial for it before relying on it. The probe banner says HERMES_HOME is redirected to scratch when --home is given; fix the wording. Related: APRV-398, APRV-310, APRV-350.

ADAPTER REBUILT ON THE OBSERVED FACTS. Three commits, no push and no pull request: the orchestrator reviews first.

WHAT THE PROBE CHANGED, and the first one is the whole task. (1) THE WORKING DIRECTORY IS REPORTED NOWHERE, so a call that does not state one is refused. Three facts from the live run combine badly: the envelope cwd is the Hermes PROCESS directory (Path.cwd() in its payload builder), the terminal tool keeps a per-session recorded directory that an earlier cd moves and that no field of the event carries, and all four file tools resolve a relative path against that same unreported directory. The model sent no workdir at all. So a verdict over such a call would bind bytes in one directory while the harness acted in another: the APRV-310 shape, on a harness that HAS the field and does not send it. hermesUnboundDirectory in src/cli/hook.ts refuses a terminal call with no absolute workdir, and a write_file, patch, read_file or search_files call whose path is relative or missing, under hook-unsupported-execution-context. Placed exactly where the Codex Bash refusal is placed and for its reason: before the open window, the gate-self path, the carry and the registration, because none of those can supply a fact the call does not carry. Absolute forms fall through to the existing gate untouched, and no other harness changes by a byte.

(2) THE REFUSAL NAMES THE RETRY, which is not politeness. The run showed what a blocked model does: it retries the same effect through another tool or another path. The refused crash write reappeared as a second write_file under HERMES_HOME/cache/scratch, and the refused garbage write reappeared as a terminal command. A refusal that did not say 'send an absolute path' would get that behaviour one tool along, which is also why every gated tool is covered rather than the shell alone. (3) THE FALLBACK OTHER ADAPTERS USE IS NOT AVAILABLE HERE. On Muse a non-absolute workdir falls back to the event cwd, which on that harness IS the session root. Here the event cwd does not even contain the work, so a fallback would be a guess. The describeToolCall fallback is untouched because Muse still needs it; on hermes it is now unreachable.

AN ABSENT PATH IS REFUSED BESIDE A RELATIVE ONE, and this is a call rather than a criterion: AC1 says 'with a relative path' and I went one step stricter, with the orchestrator's ruling on the record. The reason is the same observed fact rather than a new one. On Claude Code a Glob naming no path means the workspace, which is inside the gate root by construction, so the pass-through allow is honest there. On Hermes an unnamed target is that same unreported recorded directory: one session's writes landed in HERMES_HOME/cache/scratch and a gateway session's in the user home. CLAUDE.md says ambiguity resolves to the stricter path, so the allow that other adapters give a pathless read is an unbounded read here. If Hermes's tool schema makes path mandatory the refusal is simply inert, which is the safe direction to be wrong in.

THE VERSION FLOOR, AND WHY IT IS NOT A SEMVER. The two builds that differ on the whole fail-closed question report the SAME 0.21.3: the update that fixed the behaviour moved 670 commits without moving the version number, and hermes hooks list renders no fail_closed flag on either build, so neither the semver nor the listing can tell them apart. What did move is the build stamp and the upstream commit, both of which hermes --version prints. So core/harness-version.ts gained HERMES_FAIL_CLOSED_FLOOR (upstream 118984d7, date 2026-09-20, and one statement string every surface quotes verbatim), parseHermesVersion, and hermesFailClosedSupport returning honours, ignores or unknown. Unknown is deliberately not a synonym for ignores: two commit hashes cannot be ordered without a repository, and a health check that cried fault on every unreadable banner would train an operator to stop reading it. What guards the unknown case instead is the doc, the help block and the probe's own report, all quoting the same statement.

THE FLOOR IS READ FROM THE BINARY, NOT FROM A RECORD, and the reason is a finding of its own. hermes --version prints its build stamp behind a U+00B7, and both normalizeHarnessVersion and the schema pattern for payload.harness_version require printable ASCII on one line, so the whole line is refused and no record will EVER carry a Hermes version. The floor would have been permanently unknown if it waited for one. So the probe memo now holds the RAW first line (rawHarnessVersionLine: one line, control characters stripped, capped at 200) and the recordable form is derived from it, which keeps one spawn per process for both readers. Nothing about what a record may hold changed. Filed as APRV-419 (schema, low) with three options for a human to choose between; the likeliest right answer is recording a normalized projection rather than widening the rule.

THE FLOOR RIDES IN THE EXISTING DOCTOR ROW rather than in a new one, which was a judgement call. harness-version-unverified asks whether the binary hosting this hook is in a state where the gate is known to fire, and both findings answer it: the older half says nobody has checked since the binary changed, the new half says a broken hook would not have stopped anything. A reader who sees the row green has been told both. The floor is reported FIRST when breached, because it is the graver of the two: an unverified change means nobody has looked, while a build below the floor is established. Its fix is 'hermes update', not the self-test. Nothing else in the row moved and the three existing skips read exactly as before.

A POST EVENT IS NOT EVIDENCE THE TOOL RAN, which is the second behaviour change and was not in the criteria. post_tool_call fired 29 ms after an exit-2 deny and again after the armed hang was refused at the 300 s cap: Hermes reports the end of its own dispatch, not the end of an execution. readHermesReportedOutcome therefore treats an envelope with NO readable result as unreadable rather than as a completion, because crediting one on the event name alone would clear a failure streak (amended SPEC section 10.2) for a call that may have been blocked. A blocked call usually has no execution.started to close, since the pre half appended nothing; the case this protects is a pre half that ALLOWED followed by Hermes's own executor stopping the call (approvals.mode, a guardrail, a tool-scope check). A result object the harness DID attach, naming neither an exit code nor an error, is still read as a completion; that is the one place the reader leans generous and the doc says so.

CONFORMANCE WENT MAJOR, 1.3.0 to 2.0.0 on hook-read-scope, and the bump is honest rather than cautious. Two expectations MOVED: hermes-read-inside-relative-allows is now hermes-read-inside-relative-denies, and hermes-search-files-no-path-allows is now hermes-search-files-no-path-denies. Both vectors were RENAMED so a second implementation cannot pass by matching an id whose meaning changed underneath it. The precedent for a major here is policy-resolution 2.0.0, where a suite had stated a general rule a later task made wrong. Three vectors are new: hermes-write-relative-denies, hermes-terminal-no-workdir-denies (the exact shape a live session sent, a command and nothing else) and its control hermes-terminal-absolute-workdir-allows, which is what keeps the refusal about the unbound directory rather than about the tool. Every other harness's vectors are untouched on purpose: this answer is a fact about Hermes, and applying it to Muse would refuse calls that harness reports perfectly well.
