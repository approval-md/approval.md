## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The values block separates `wants` (behaviour asked of the agent) from `like` (what the work is graded by). Carter finds the distinction thin and wants one list. Decision: bump `version` to the integer 2 and drop `wants`; a version-1 block is refused by the values loader with a message naming the migration (fold wants into like, set version: 2). Only this repo carries a values block and the block is inert guidance (SPEC §11.1 invariant 10), so a hard cut is cheaper than dual-version loading. A v1 block fails the values loader only, never the policy loader (SPEC line 73 rule holds). After this lands and before Carter pastes the v2 block, `approval values` in the primary reports the current block as malformed; the PR description and handoff must say so with the paste and re-attest commands. Touches invariant 10 only to keep it: tests/values-inert.test.ts passes unchanged.

Decisions:
- Version is the quoted string "0.2" (type string, const "0.2"), matching the policy block's "0.1". The schema's version description now argues from that: two blocks in one file, one version style, and the quotes are load-bearing because YAML reads a bare dotted identifier as a float.
- New ValuesLoadFailureCode member: `version-unsupported`, chosen to sit beside file-missing / multiple-blocks / unterminated-fence / yaml-error / schema-invalid. It fires BEFORE schema validation and only for a NUMBER in the version position, because a number there is always YAML having read the version rather than an author mistyping a key: 1 gets the migration message (fold `wants:` into `like:`, set `version: "0.2"` with the quotes, and the block fails the values loader alone), 0.2 gets the quoting message, any other number gets both. Every non-numeric wrong version (the string "1", a list, a map) still goes to the schema, whose const violation is the truest thing about it.
- The AGENTS.md importer now drafts every bullet into `like` (the middle grade) instead of the retired `wants`, and still never writes `love` or `dislike`. ValuesDraft.wants became ValuesDraft.like; the draft header says how strongly a line is meant is the human's to say.
- doctor's values-block FAIL fix line is special-cased for `version-unsupported`: it names the three edits plus the re-attestation rather than the load code, because that block is a correct document of the wrong vintage rather than a broken one.
- schema/fixtures/values/invalid/version-string.json was replaced by version-integer.json (1), version-float.json (0.2) and version-wrong-string.json ("0.1"); two new whole-file fixtures, schema/fixtures/values-md/invalid/version-1.md and version-unquoted.md, drive the loader and CLI refusal tests. conformance/vectors/schema-validation.v1.json and the manifest were regenerated with scripts/regen-conformance-vectors.mjs.

The exact replacement text for the second paragraph of §5.3 (SPEC.md line 160, replacing the sentence that begins "The block is optional, at most one per file") is:

The block is optional, at most one per file, and carries the info string `yaml approval-values`. Its schema (`values.schema.json`) is closed and small: `version` (the quoted string `"0.2"`, required), three standing lists `love`, `like` and `dislike` (what the human grades the work by, and `like` is also where what the human asks of the agent as behaviour lives: honest opinions on the work, a short journal entry per milestone, an early "I am stuck"), and `communication`, a single string saying how the human reads and answers. An earlier revision carried those requests in a separate `wants` list; they are folded into `like` because a request about behaviour and a preference about the output are graded by the same person in the same way, and one list is easier to keep true than two whose boundary has to be re-decided on every edit. The version is spelled as the policy block's `"0.1"` is, and the quotes are required, since YAML reads a bare dotted identifier as a float; it replaces the integer `1` of the first revision, and a block still carrying that integer fails the values loader alone and never the policy loader, exactly as §5 says of every values failure. There is no `indifferent` list, because a list of things one is indifferent to is empty by construction, and there is no `hate`, because a fourth grade invites a ladder the human has to maintain while the event vocabulary of §5.2 already carries intensity where it is observed. Nothing class-shaped is admitted: a key that named a class would be policy wearing a different fence, and the invariant below would become unprovable. (Amended APRV-336, pending sign-off.)
