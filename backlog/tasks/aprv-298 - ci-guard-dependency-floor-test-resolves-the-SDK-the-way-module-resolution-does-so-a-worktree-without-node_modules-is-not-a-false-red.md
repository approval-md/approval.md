## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The dependency-floor case in tests/ci-guard.test.ts reads each production dependency package.json by joining REPO_ROOT with a literal node_modules path segment. REPO_ROOT is derived from the test file, so in an agent worktree that has no node_modules of its own the path points at a directory that does not exist and the case dies with ENOENT on the @modelcontextprotocol/sdk entry. Node itself would resolve that package from the same file without trouble: module resolution walks up the parent directories and finds the primary checkout install. The test hard-codes one directory instead, so it reports a missing install as a violated Node floor. That is a different claim and an untrue one.

The cost is measured. Three separate tasks re-diagnosed this same ENOENT tonight before reaching their own work: APRV-220 on human-signed log checkpoints, APRV-230 on phantom daemon ticks, and APRV-286 on the sandbox-probe control test. Every lane that runs the suite from a worktree pays the diagnosis again, and a red that is never the lane fault trains lanes to discount reds.

Fix the resolution rather than the floor check. Locate each dependency package.json the way Node would, and when the package is genuinely absent everywhere, skip with a named reason so an absent install reads as absent rather than as a floor violation. One wrinkle to plan around: the @modelcontextprotocol/sdk exports map does not list its own package.json subpath, so a bare createRequire resolve of that subpath throws ERR_PACKAGE_PATH_NOT_EXPORTED and the walk-up fallback is what carries it.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Add a resolver helper near the dependency-floor case in tests/ci-guard.test.ts: given a dependency name, return the absolute path of its package.json, or null when nothing on the resolution path has it.
   a. First try createRequire(import.meta.url).resolve(name + "/package.json"), which is what Node module resolution answers when the package exports that subpath.
   b. On any throw, fall back to walking up from the test file directory and testing <dir>/node_modules/<name>/package.json with existsSync. This is the same parent-directory walk resolution performs, and it is what carries @modelcontextprotocol/sdk, whose exports map omits ./package.json and therefore makes step a throw ERR_PACKAGE_PATH_NOT_EXPORTED.
2. Rewrite the loop body to read through that helper. Drop REPO_ROOT from this case entirely; REPO_ROOT stays for the workflow files, which are checked-in bytes and belong to the repo.
3. Turn the case callback into (t) => and, when the helper returns null for a dependency, call t.skip with a reason naming the dependency and saying the install is absent from every node_modules on the resolution path, then return. An absent install is an unproven floor, not a violated one, and the named skip says which.
4. Keep the unreadable-range assertion exactly as it is: a range shape the parser cannot read still fails. Only the location of the bytes changes.
5. Extend the comment block above the case to record why the path is resolved rather than joined, citing the lanes that re-diagnosed the ENOENT.
6. CHANGELOG entry under Unreleased.
7. Verify: npm run build, then node --test dist/tests/ci-guard.test.js from this worktree, which has no node_modules of its own, and npm run lint.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Changed tests/ci-guard.test.ts only, plus a CHANGELOG entry. The dependency-floor case now calls a new resolveDependencyManifest helper instead of joining REPO_ROOT to a literal node_modules segment. The helper asks createRequire on import.meta.url first and falls back to walking the parent directories for node_modules/<name>/package.json, which is the same chain module resolution searches. When neither answers, the case calls t.skip with a reason naming the dependency and saying the floor is unproven rather than violated, so an absent install reads as absent. REPO_ROOT stays for the workflow files and for the repo package.json, which are checked-in bytes present in every checkout.

One finding changed the shape of the fix. A bare createRequire resolve of @modelcontextprotocol/sdk/package.json does not throw as expected: the exports map ends in a "./*" wildcard, so the subpath resolves to dist/cjs/package.json, the two-key type-commonjs stub the build writes. That file parses and declares no engines, so the loop would have skipped the dependency that motivated the whole task and the guard would have passed while proving nothing about it. Two defenses: the helper accepts a resolved manifest only when it names the package it claims to be, and the loop asserts the same thing on whatever it ends up reading, so a future stub fails loudly instead of dropping a floor claim.

Evidence. AC1 and AC2: npm run build gave build-ok and node --test dist/tests/ci-guard.test.js exited 0 with 31 pass, 0 fail, 0 skipped, run from a worktree that has no node_modules of its own, so every dependency was read out of the primary checkout install found by the walk. A probe script running the shipped resolver logic from two roots, the worktree file and the primary checkout file, resolved all five production dependencies to the same five primary manifests and returned null for an absent package name, so the skip branch is reachable and the walk terminates at the filesystem root. AC3: entry added under 0.1.0 unreleased. npm run lint exited 0.

Scope note: a grep for node_modules across tests, src, scripts and conformance found no other read of an install path, so this was the only case with the defect. No global invariant in SPEC section 11.1 is touched; the change is test-side path resolution and adds a check rather than relaxing one.
