## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
From the APRV-475 refuter (PR #611, 2026-10-05), reproduced on the PR build. After the wait finds a grant, the hook passes the shared pause (BEFORE_SPEND, src/cli/hook.ts) and then calls consumeGrants -> consumeHarnessGrant (src/core/gate.ts), which does a full verified read and an append that waits on acquireLock (src/core/log.ts, DEFAULT_LOCK_TIMEOUT_MS = 2000, sleepSync retries), possibly repeated by withHeadMovedRetry. That stretch is synchronous, so a SIGTERM delivered during it is held while the wait's listener is registered, and then DROPPED when the wait's finally removes the listener (a held signal whose last listener is removed is discarded; scratch repro dropped.mjs prints survived on Node 24 and 26). Repro lockrace.mjs: hook claude-code, --interval 1500ms, grant recorded, another writer holds events.jsonl.lock (the daemon does this routinely), SIGTERM 1.7 s later while the hook spins on the lock, lock released 100 ms after: exit 0, an allow on stdout, one execution.started appended AFTER the signal; same on hermes (inherited from APRV-473). The docs and the proposed SPEC §10.1 hunk carve out 'the spend itself' as the residue, but that stretch can be seconds under contention on a large log (the live log is ~53 MB). Side observation, pre-existing: the start record's ts is taken before the lock wait, so under contention it can predate its append by about a second. Decide whether the carve-out may include lock contention; if not, make the lock wait yield inside the generator (try the lock, and on contention yield the retry interval so each retry crosses a poll phase), then take a final zero pause immediately before the consume, shrinking the residue to the read and append under the lock.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. src/core/log.ts: export appendLockHeld(logPath), a read-only advisory probe of <log>.lock (existsSync); the lock protocol itself (open wx, never stolen, head compared under the lock) is untouched.
2. src/cli/hook.ts: one generator helper, spendUnderLock(run, attempt), that every hook spend goes through. Per round: while the lockfile is present and the round's lock budget (append.lockTimeoutMs ?? 2000) is not spent, yield the retry interval (append.lockRetryMs ?? 20) so each retry crosses a poll phase; then yield BEFORE_SPEND (the shared zero pause, now taken immediately before the consume); then run the whole spend once with lockTimeoutMs 0, so the append tries the lock exactly once and never sleeps synchronously. A lock-timeout refusal after the lock was seen free (another writer won the race) starts a new round, up to HEAD_MOVED_ATTEMPTS rounds; one after the budget ran out with the lock still held is final (append-failed / lock-timeout, deny, fail closed). Compare-and-append is unchanged: each attempt is a fresh verified read and an append against the head it read.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Decision on the carve-out: lock contention may NOT be part of the residue. The wait for the log's lock now yields inside the generator, and the shared zero pause moved after it, immediately before the spend's one attempt.

Approach. src/core/log.ts exports appendLockHeld(logPath) (an advisory existsSync probe of <log>.lock: takes no lock, writes nothing, authorizes nothing) and the two lock defaults (DEFAULT_LOCK_TIMEOUT_MS 2000, DEFAULT_LOCK_RETRY_MS 20) so a caller waiting on its own loop keeps the same numbers. The lock protocol itself is untouched: open wx create-or-fail, never stolen, head compared under the lock. src/cli/hook.ts adds spendUnderLock(logPath, append, attempt), a generator every hook spend goes through. Per round: while the lockfile is present and the round's budget (append.lockTimeoutMs ?? 2000) is not spent, yield min(retry, left) (retry = append.lockRetryMs ?? 20, floored at 1 so driveSync never spins); then yield BEFORE_SPEND; then ONE attempt of the whole spend with lockTimeoutMs 0, so its append tries the lock once and never sleeps. A lock-timeout after the lock was seen free (another writer won the race between probe and try) starts a new round, up to HEAD_MOVED_ATTEMPTS (3) rounds; a lock-timeout after the budget ran out with the lock held throughout is final (append-failed / lock-timeout, deny, nothing appended), its message extended to say how long the spend waited and why (APRV-478). Routed through it: consumeGrants (carried spend and post-wait spend) and recordUnattended (supervised and autonomous charges), both now generators, one spendUnderLock per key/class; runBypass's recordGateBypass (its decided read seeds round 1 only, later rounds re-read). The per-site 'yield BEFORE_SPEND' folded into the helper, so an uncontended spend still has exactly one zero pause between the read that found a grant and the append (the APRV-475 stepped tests pass unchanged). At the post-wait site the order is now leaveWait, callerGone, then the helper's pause; leaveWait and callerGone are no-ops on the CLI and the zero pause is no pause under driveSync, so neither route changes.

Residue now: from the last pause to the record, the spend's own verified read, one try at the lock, the append, and verifySpent's read after it. Milliseconds, never a wait on another process.

Synchronous drivers (AC2). commandHook (in process, serve worker) and decideHarnessCall (Codex bridge) run the same steps under driveSync, which sleeps each yield with Atomics.wait: a held lock still blocks them for the same 2 s at the same 20 ms cadence as acquireLock did. One stated difference: the 2 s bound is counted per round of the spend, where it was per head-moved attempt inside the writer, so a log under sustained contention is refused no later than before and sometimes sooner (the stricter direction). The serve worker still re-takes its store lock in leaveWait before the spend, unchanged. serve-hook, serve-concurrency and codex-bridge pass.

Side effects stated. (1) Each attempt's ts is taken after the lock wait now, so the start record's ts predates its append by the read only (the side observation in the description is fixed). (2) Inside a spend attempt every append is single-try, including the budget.exceeded evidence record on a budget refusal; if another writer holds the lock at that exact instant the refusal stands (still a deny, invariant 8) and its message says the evidence could not be appended, where before that append waited up to 2 s. The window is the instant after the probe saw the lock free. (3) A multi-key/multi-class spend now passes the pause before each key; a signal between two keys blocks with the first key spent, the same trade consumeGrants already documents for a failure on the second key. (4) Hermes pre-wait: a signal during an unattended charge's lock wait now reaches the early guard at a retry pause (block, nothing spent); the other harnesses register no listener there (default disposition, APRV-477's scope, untouched).

Invariants touched (SPEC 11.1): 5 compare-and-append unchanged (every attempt is a fresh verified read plus an append against the head it read, the lock taken by the same atomic create-or-fail; the probe decides nothing); 8 unchanged (a lock-timeout still denies, nothing allowed without its record); 1 unchanged (verified reads only); 2 untouched (ts assigned by the gate at attempt time, nothing from the caller); 6 unchanged codes (append-failed with the writer's lock-timeout; hook-interrupted on the block). No execution.started after an interruption now holds through lock contention, pinned below.

Tests. tests/harness-spend-lock-wait.test.ts (21): the held-lockfile repro through the bin for claude-code, cursor, codex, grok, muse and hermes (grant appended in process with the lock taken in the same synchronous stretch, SIGTERM 700 ms into the spend's lock wait, lock released 100 ms after: the harness's own interruptedWaitDirective bytes at its exit code, no execution.started, no withdrawn over the grant, and an identical retry carries the unspent grant, one start); the grant racing the signal under contention, 10 concurrent runs alternating order, for claude-code, grok and hermes (every run blocks, no start, exactly one of granted/withdrawn); no-signal controls for claude-code, codex and hermes (lock released inside the bound: allow, one start; lock held past it: deny hook-gate-refused:append-failed, lock-timeout, nothing appended, grant still standing); a stepped in-process test per harness (with the lock held the spend yields DEFAULT_LOCK_RETRY_MS three times with nothing spent; after release the next step is the zero pause with nothing spent; the step after appends and allows). tests/log.test.ts: the module-surface pin lists the probe and the two constants with the reason none mutates. tests/harness-wait-interrupt.test.ts: a comment that named APRV-478 as open.

Proposed SPEC.md section 10.1 hunk, PENDING SIGN-OFF for the next attestation batch (supersedes APRV-475's revised hunk; SPEC.md, APPROVAL.md and .approval/ untouched), placed after 'A harness wait that expires, and the question it leaves behind':

**A harness wait that is interrupted.** An adapter whose process receives a termination signal (SIGTERM or SIGINT) while it waits on a human MUST end the wait within one poll interval and MUST answer a block in its harness's own dialect, at the exit code that harness reads as one, before it does anything that can wait on the log; when its output cannot be written whole it MUST exit with the code that harness reads as a block on an empty output. It MUST then withdraw the requests it opened (approval.withdrawn, reason cancelled), and MUST NOT record execution.started for that tool call: the harness that sent the signal has abandoned the call. A grant recorded before the signal is dispatched is left standing and unspent, since the withdrawal is refused already-decided and nothing is written over a decision. A request the adapter adopted from an earlier call is left alone, since a withdrawal is the requester's own. A wait that cannot observe a signal until it returns, such as a synchronous sleep, does not meet this rule, and that includes a spend's wait for the log's lock: an adapter MUST wait for another writer in a way that observes a signal, and MUST give a pending signal one chance to be observed after that wait and immediately before the spend, so a signal held through the synchronous stretch before a spend, or arriving while the spend waits for the lock, blocks it. What remains is the spend itself: its read of the log, its single attempt at the log's lock, and its append. An implementation MUST state that residue wherever it states this rule, and a signal there is answered by the verdict already reached. (Amended APRV-475, APRV-478, pending sign-off.)
