## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Carter's feedback after the Muse (APRV-350) and Hermes (APRV-398) probes on 2026-09-21: both were very manual, with prompts, restarts and file checks copied into terminals by hand, and more harnesses are coming (Grok Bot, others). The manual cost came from three sources and only one is the gate: launching a harness is harness.launch.* and manual by policy, which is right and costs one tap; the probes assumed an interactive TUI session, which is a design choice; and the model key must be in the harness home, which agents do not touch. Convention to build: scripts/probes/<harness>.mjs gains a run mode that drives the entire matrix itself through the harness's one-shot invocation (hermes -z PROMPT --in DIR --accept-hooks; claude -p; codex exec; the Muse equivalent), including writing the hook block, running each armed trial as a child process, waiting out the hang trial, reading the effects, and writing the report, with canned-envelope tests so the driver is verified before any install. The lane then files ONE request classified harness.launch.<kind> for the driver invocation (with APRV-401 the grant binds the driver bytes), the human taps once, and the report comes back to the lane. The driver records the exact version string before any trial and refuses to report against a build below a known floor (the Hermes probe ran its first pass on a build 670 commits behind and every result was wrong for that reason). The report distinguishes an armed call that was blocked from a file that exists, by reading its own capture for later calls naming the same path, which is the heuristic that misread the Hermes garbage trial. Credentials: document the two options, a key placed once by the human in the harness home, or a vault entry injected through approval run's credential window. The messaging-gateway pass stays a short manual step (a bot cannot message a bot) and the driver prints exactly the messages to send. Retrofit the Hermes probe first as the reference; Muse second if its one-shot mode exists. Related: APRV-350, APRV-398, APRV-415, APRV-401, APRV-243 (Grok Build probe), APRV-246 (Grok Bot).

2. THE DRIVER SHAPE, decided once and applied twice. A probe gains a run verb that does in one process what the runbook asked a human to do in thirty steps. Its order is fixed and the order is the safety property: (a) spawn the harness binary with its version flag and record the RAW first line before any trial; (b) compare it against a floor carried as data in the probe and refuse outright below it, because a round measured on a build that ignores the key is a day lost and that is exactly what happened on 2026-09-21; (c) build the scratch project and write the hook block; (d) walk a declarative matrix, arming each trial through the same control file the manual path uses and spawning ONE one-shot invocation per trial; (e) print the report. No prompt is typed and no restart is asked for, because every one-shot invocation is its own process start, which is what makes the fail-closed pairs drivable at all: the config is read at startup, so rewriting it between trials needs no human.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
DELIVERED AS ONE TAP PER PROBE, AND THE COST IT REMOVES IS NAMED IN THE PAGE RATHER THAN IN THIS FILE.

WHAT THE DRIVER IS. scripts/probes/hermes-hook.mjs gained a run verb that does the whole round in one process: the version first, then the scratch project and the hook block, then a declarative matrix of twenty steps driven through one one-shot invocation each, then the report. Twenty prompts typed into an interactive session were twenty harness.launch.hermes classes, manual by policy, which is where the afternoon went; the driver is one.

THE ORDER IS THE SAFETY PROPERTY, and this is the part to review. The version is read BEFORE the config is written, not before the first trial. A build below the floor is refused with nothing installed anywhere, so a refused build has no hook block sitting in its home and the operator has nothing to undo. A test pins that by comparing the pointer file before and after the refusal. An UNREADABLE version refuses too, naming an explicit override flag, and that is a judgement worth arguing with: core harness-version.ts deliberately treats unknown as distinct from ignores, because a health check that cried fault on every unreadable banner trains an operator to stop reading it. A DRIVER is a different reader. It is about to spend a human's launch grant on a round whose headline nobody could trust afterwards, so it refuses and says which flag overrides it. Same fact, two readers, two right answers.

THE FAIL-CLOSED PAIR IS THE THING THAT ONLY A DRIVER CAN GET. Switching fail_closed needs the harness restarted, because the config is read at startup, and a one-shot invocation IS a restart. The 2026-09-21 round ran pass A only for exactly that reason and the report had to grow labels to say so honestly. The driven round gets both passes for free, and the suite asserts it: with the key every broken hook is withheld, without it every effect happens, and the report prints CONFIRMED.

THE FLOOR IS A COPY, AND THE COPY IS PINNED. The probe is plain ESM an operator runs from a checkout before any build, so it cannot import the compiled module. Two tests hold it to the runtime: the constant deep-equal to HERMES_FAIL_CLOSED_FLOOR, and the READING of it agreeing with hermesFailClosedSupport on five version lines including the two real ones. A probe that parsed the line differently from the doctor row would refuse rounds the doctor passes, which is the worse direction.

THE RETRY HEURISTIC GOT SHARPER, which is AC1's last clause. A driven step is one one-shot process, so arm writes a step label and record copies it into every envelope that step produces. The label SURVIVES the arm being consumed, deliberately: the interesting calls are the ones the model makes after its armed call was refused. The report now says whether a later call naming the armed artifact was a retry INSIDE that session (the confound that misread the garbage trial) or a different step's file entirely (a different process, so the armed call is not implicated). A hand-armed round carries no label and reads as it did before.

THE EARLY ABORT. If the first invocation captures no envelope the driver stops rather than burning nineteen more on the same silent failure, and names three causes in the order they are worth checking, first among them the one-shot spelling. That spelling is UNVERIFIED in this repository and is a template with placeholders that a flag overrides, so a wrong guess is a flag rather than an edit to the script. This is the one place I deliberately built for being wrong: nothing here has run either binary.

THE FAKE HARNESS BINARIES ARE THE POINT OF THE SUITE. tests/fake-hermes.mjs answers the version flag, READS THE CONFIG THE PROBE JUST WROTE to find the hook command and its fail_closed, fires the hook with a canned envelope on stdin, applies the verdict semantics the live round measured, and performs the effect when nothing blocked. A stubbed spawn function would have proved the loop calls something; this proves the round a human would get, and it exercises the hand-emitted YAML, which is the artifact that cost the first Hermes round a day. tests/fake-grok.mjs is the same shape and its header LABELS THE DIFFERENCE: it models DOCUMENTATION, because nothing here has run Grok Build, and a fake that quietly modelled documentation would turn an open question into an apparent answer.

THE GROK PORT REMOVED A POLICY.CORE HAND-EDIT NOBODY ASKED ME TO REMOVE. The old runbook had a human add a probe entry to this repository's own Claude settings file and remember to take it out again; that file is policy.core and a probe entry left behind is a hook that answers nothing. Both candidate registrations now go in a scratch project the driver builds, each naming its own --config-id, so ONE round answers which file a session of that harness reads instead of two rounds answering it one at a time. The native hook file is registered as the CONTROL: a round where nothing fires is inconclusive rather than reassuring, and the report says so in those words.

TWO DELIBERATE DIVERGENCES BETWEEN THE TWO PROBES, both recorded because a convention that hid them would be a worse convention. (1) Grok has NO version floor, because no build difference has ever been measured for it; VERSION_FLOOR is null and the driver says so rather than inventing one. An invented floor is the confident-stale documentation this project exists to avoid. (2) On Grok the arm is per STEP when driven and per CALL by hand. Both registrations fire for one tool call, so a per-call arm would leave the second entry answering something else and the trial would be two variables. Hermes keeps one-arm-one-call because that is the behaviour its live round measured and the retry caveat is built on it.

INVARIANTS TOUCHED, SPEC section 11.1, as CLAUDE.md requires. RAW SECRETS NEVER APPEAR IN THE LOG: both probes redact token-shaped strings before anything reaches disk, the Grok redactor gained the xai- prefix, and the driver's run log stores only redacted tails of a child's streams. SELF-REPORTED FIELDS NEVER REDUCE SCRUTINY: the version a binary prints can only make the driver refuse, never widen anything, and a build claiming a later date buys nothing except defeating a refusal that would have asked a human to look. FAIL CLOSED: an unreadable version refuses, a config the probe cannot safely edit refuses and touches nothing, a first invocation that captured nothing aborts, and a path the jail cannot place counts as outside. HUMAN-ONLY CLASSES ARE INERT TO AGENTS: neither driver runs a harness on its own account; both exist to be run once through approval run on a granted token, and no agent ran hermes or grok in this task. GUIDANCE NEVER REACHES ENFORCEMENT: nothing in these scripts is read by any verdict path. Nothing in src/ changed at all, which is why the conformance vectors and every adapter suite are untouched.

WHAT IS NOT DONE, AND WHY. Neither live round ran: APRV-398 AC1 is already checked from the 2026-09-21 round, and APRV-243 AC1 stays Carter's and stays UNCHECKED, which is the instruction. The one-shot flag spellings for both harnesses are unverified guesses with an override. The Muse probe was NOT ported: the task says Muse second if its one-shot mode exists, and nothing in this repository establishes that it does, so guessing a third spelling would add a third unverified claim for no measurement. The vault credential route is documented WITH ITS GAP stated: no adapter serves harness.launch.*, so there is no requiredCredentials declaration to keep a variable alive, and option 1 (a key the human places once in the harness home) is the supported one today.
