## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Observed 2026-09-19 ~22:0xZ in the primary: approval up stopped with "daemon: stopped (anchor-diverged) after 1489 tick(s)", "refs/approval/advance/records-log-2026-09-19 anchors seq 55084 at e53ed3e6... and the working log carries no record at that seq. These are two chains, not one. ahead by 171: the committed chain (seq 55084 e53ed3e6...) is a prefix of the working chain (seq 55255 9c0c476a...)". Read-only check right after: approval log verify clean at 55280; sed -n 55084p on the working log shows seq 55084 hash e53ed3e6..., the exact record the anchor names; the anchor ref file holds c040cd77, the records commit of PR 491 (merged 21:38Z). So the working log carries the record, the message says both that it does not and that the committed chain is a prefix of it, and the daemon stopped on a divergence that does not exist. Sequence that day: the orchestrator ran approval log advance --pr from the primary at 21:16Z (PR 491) while the daemon was up; Carter ran approval log sync in the primary at ~20:0xZ and again later ("snapshot restored over the pulled baseline"), each time under the running daemon; the policy amendment making log.advance.daemon autonomous (seq 53366, PR 485) and a daemon restart happened between. Hypotheses to test in order: (1) the anchor check compares the anchor against the daemon in-memory chain view, which a sync that rewrites the working file underneath the process leaves stale, so the record is missing from the VIEW and present in the FILE; (2) the message builds both sentences from different sources (file for the prefix claim, view for the missing-record claim). Fix: the anchor check reads the file through the same verified read the tick uses and re-reads before declaring divergence; a stop message never asserts two contradictory facts (if the prefix claim is true the verdict is not diverged); a sync under a running daemon is either refused (the daemon is the single writer) or the daemon notices the file changed and re-reads. Related: APRV-215 (sync refuses on dirty working log), APRV-284 (advance arms itself), APRV-382 (daemon cadence advance), APRV-125.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Read the anchor check (src/cli/log-anchor.ts), the tick that calls it (src/daemon/daemon.ts), log-reconcile, state.ts verified reads, log-sync and log-advance. Confirmed hypotheses 1 and 2 in the code: checkLogAnchor reads the working FILE itself with readFileSync for the byte and digest checks, then asks the CALLER-supplied records (the tick opening read) whether a record sits at the anchor head seq. When the file grows or is rewritten between the tick read and that readFileSync, the digest check passes on fresh bytes while the head lookup fails on a stale view, and the divergence sentence is then built from the file again, which is how one message says both "carries no record at that seq" and "ahead by N, the committed chain is a prefix of the working chain". A log sync in the primary is exactly that rewrite: it baselines the working log to the committed bytes, fast-forwards (version control writes the file, not atomically), then restores the snapshot, all while the daemon reads without the append lock.
2. Restructure checkLogAnchor around one pure comparison of (anchored copy, working bytes, records) with four answers: pass, behind, diverged, and moved. Moved is new and internal: the bytes and the view contradict each other, which is never evidence of a fork. After the prefix digest matches, the file provably carries the anchored head record inside those bytes, so a view that lacks it is moved, never diverged. The shorter-than-anchor branch gets the mirror check.
3. On moved or diverged, read the file once more and re-derive the records through readVerifiedRecords with cache disabled, which is the sanctioned verified read, then run the same comparison on that fresh pair. A confirmed divergence stops the daemon as before; a pass or behind from the fresh pair carries a reread marker (both heads plus one sentence); a second incoherent pair is a skip that says the file is moving underneath the check, because a check that could not look must not report a pass and must not report a fork either.
4. Rewrite the divergence message so it cannot assert two contradictory facts: the chain comparison is quoted only when it also says diverged, where it names the first divergent seq and both heads; when the chains agree while the bytes do not (a re-serialized log) the message says that affirmatively and claims no prefix.
5. AC3 decision: the daemon re-reads and logs one line, and log sync is not made to refuse. Reasons recorded in the notes and in docs/dogfood-cutover.md. New daemon warning code anchor-reread, emitted whenever a check carried a reread marker.
6. Tests. In tests/log-anchor.test.ts, a unit reproduction handed the view the tick held before the sync landed (built through the real append path, the pre-sync state copied aside as bytes), asserting a pass with the reread marker and no anchor-diverged. A daemon-level reproduction that interposes the sync bytes DURING the check: a real version-control binary wrapped by a small node script first on PATH, which copies the post-sync file over the working log on the first call made after the tick opening read (detectable because that read publishes the verified-head snapshot and nothing before the first tick reads the log when the cadence advance is off), then delegates to the real binary. Assert the tick continues, the anchor line says pass, and one warning line was emitted. Keep the existing diverged cases red-hot: the truncate-and-rechain forgery and the re-serialized prefix must still refuse.
7. Docs: docs/dogfood-cutover.md gets the decision and the runbook line; docs/cli-reference.md gets the anchor bullet updated with the re-read and the new warning.
8. Verify: build, typecheck, lint, then the daemon, advance, sync, log-anchor, log-reconcile and verified-snapshot suites, then a full test run compared against a clean baseline.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
ROOT CAUSE, both hypotheses confirmed in the code and then reproduced in a test. The anchor check proved two facts from two DIFFERENT reads. Fact one, the bytes: the working log prefix must hash to the anchored digest, read by the check itself with readFileSync. Fact two, the head: a record at the anchored seq carrying the anchored hash, looked up in the records the CALLER had verified earlier and handed in. The daemon hands in the tick opening read, and approval log sync rewrites the log file three times (the baseline write, the fast-forward, the snapshot restore) while the daemon reads without the append lock. A tick whose opening read landed inside that window therefore held a view the file had already moved past, fact one passed on the new bytes, fact two failed on the old view, and the divergence suffix then re-read the file for a third opinion. That is how one message said both that the log carries no record at seq 55084 and that the committed chain is a prefix of the working chain 171 records back. Hypothesis 2 is the same seam: the two sentences were built from different sources.

THE FIX, in src/cli/log-anchor.ts. One pure comparison over one triple (anchored copy, working bytes, a view of them), with four answers rather than three. The new answer is moved: the bytes and the view cannot both describe one file. Once the anchored prefix is present byte for byte the anchored record is INSIDE those bytes by construction, so a view that lacks it, or carries another hash there, is stale and is never evidence of a fork. The mirror case is covered too: bytes shorter than the anchored copy and not a prefix of it, while the view claims the anchored head, is also moved rather than diverged. On moved, and on diverged, the check reads the file once more and re-derives the records through readVerifiedRecords with the cache off, a cold walk from genesis, which is the sanctioned verified read the caller itself used, then runs the same comparison on that fresh pair. A confirmed divergence still stops the daemon. A pass or behind from the fresh pair carries a reread marker holding both heads and one sentence. A pair that is incoherent TWICE is a skip naming that, because a check that could not look must not report a pass and must not report a fork either, and the next tick asks again over bytes that have settled.

MESSAGES. The chain comparison is quoted only where it agrees that the chains parted, and there it names the first divergent seq and both heads. Where the record hashes agree as far as both copies go while the bytes do not, which is the re-serialized log, the message says that affirmatively and claims no prefix in either direction. So the two-fact sentence is unreachable: the missing-record half is gone from every refusal path, and the prefix half is quoted only where it is consistent with the verdict.

THE DAEMON. One new warning code, anchor-reread, emitted when a check carried the marker. One line, no stop, and no other daemon behaviour touched: a sync or a records pull replacing the log under this process is housekeeping on the container, sync holds the append lock for its whole ceremony so nothing could interleave with an append, and every other step of the tick re-reads the log for itself already. The line exists because a writer nobody expected is a thing to know, and because this is the read that used to be reported as a fork.

AC3 DECISION, and why it went the way it did. The daemon re-reads and logs one line. Sync is NOT made to refuse while a daemon holds the log. Four reasons, all recorded in docs/dogfood-cutover.md. Sync is the repair for a dirty working log plus an upstream change (APRV-215) and the daemon is up in the primary nearly always, so a refusal would mean stopping the daemon to sync, which is the hand ritual APRV-125 and APRV-292 each retired. Nothing tells a verb that a daemon holds the log: there is no lease, the append lockfile is taken per append and sync holds it itself, and a lease left behind by a crash would refuse the very sync that repairs the checkout, which fails stuck rather than closed. In this window the daemon is a reader and not a writer, so the only damage was the check own stale view. And fixing the reader covers every other writer of that file, a records pull or a restore by hand included, where refusing one verb covers only that verb. No code in src/cli/log-sync.ts was changed and the CLI output of log verify with the anchor flag is byte-identical: the reread marker is additive on a type whose JSON shaping selects fields explicitly.

INVARIANTS TOUCHED, SPEC section 11.1. Invariant 1, enforcement paths read only verified records: both sides of every comparison stay verified, and the second opinion is the sanctioned verified read rather than a walk written here. Fail closed where the runtime controls the outcome: a real divergence still stops the daemon, on byte evidence read twice, and the incoherent case is a skip that says so rather than a pass. Nothing here appends, so compare-and-append and the append-only rule are untouched, and no log line is written by hand anywhere in the tests.

TESTS. Five new cases in tests/log-anchor.test.ts. The reproduction: a repository whose committed copy is anchored by a real advance ref at seq 3, a view captured at seq 2 before those records were in the file, and a working file at seq 5. Pre-fix that is the observed refusal verbatim, post-fix it is a pass, ahead by 2, with the marker naming seq 2 against seq 5. The other direction, a working log behind the anchor with a view older still, is behind. A real divergence still refuses and its message names DIVERGED at seq 3 and asserts no prefix. A re-serialized prefix still refuses on the bytes and says re-serialized rather than quoting the chain comparison as equal.

The daemon case interposes the sync DURING the check, which needs a process outside this one: a tick is synchronous, so nothing in-process can write the file in that window. The only other process a plain tick starts is the version-control binary the check runs to resolve the anchor, so the writer rides in there. The test puts a small node script named for that binary first on PATH; on the first call made after the tick opening read, detectable because that read publishes the verified-head snapshot and with the cadence advance off nothing before the first tick reads the log, it copies the post-sync file over the working log and then delegates every argument to the real binary, which it locates by scanning PATH. The bytes it copies came from the real append path in the same repository. Assertions: the daemon does not stop, the tick line reports anchor pass at seq 3, exactly one anchor-reread warning. Fragility to know about: it depends on that binary being on PATH and on the snapshot publication, both asserted inside the test, and it fails loudly rather than silently passing if either changes.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
The false anchor-diverged came from proving two facts from two reads: the byte and digest comparison from the check own read of the working log, the record-at-the-anchored-seq lookup from the records the caller verified earlier. A log sync rewriting that file under a running daemon leaves the second stale, so the bytes said the anchored prefix is here and the view said the anchored record is missing, and the message carried one fact from each. The check now runs one comparison over one triple, treats a view that disagrees with the bytes as moved rather than diverged, re-reads the file once through readVerifiedRecords with the cache off before any refusal, and quotes the chain comparison only where it agrees that the chains parted. A real divergence still stops the daemon on byte evidence read twice. AC3 decision: the daemon re-reads and logs one anchor-reread line, and log sync is not made to refuse, because there is no lease that could say a daemon holds the log, sync is the repair operators need while the daemon is up, and the daemon is only a reader in that window. Verified: build, typecheck, lint exit 0; log-anchor 35 of 35 pass with five new cases including a daemon tick that has the sync land in the middle of the check; a 374-test daemon, advance, sync and verified-read matrix all pass; full npm test 4841 of 4864 with only the 22 known SMTP failures of this environment. The reproduction was validated by restoring the old decision in the built output and watching the three new cases fail with the observed message.
