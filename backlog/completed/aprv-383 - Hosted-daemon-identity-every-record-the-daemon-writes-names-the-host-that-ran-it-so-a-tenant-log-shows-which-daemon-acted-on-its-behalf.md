## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Carter asked on 2026-09-19 how a records advance and the rest of the daemon work when the daemon is hosted by one party for another (an external approval.md user whose repo, log and policy are their own). Three properties already hold or are near: authority comes from the tenant attested policy and never from the host (a manual class prompts the tenant phone through their sender mapping, APRV-324 and 356); credentials come from the launch environment only, so one process per tenant with a token the tenant issued and scoped to their repo; and decisions arrive only through the tenant mapping, so the host cannot mint one. What is missing is identity: records the daemon appends (audit.sampled, audit.dark_session, log advances, gloss, channel bookkeeping) carry a generic daemon actor, so a tenant reading their own log cannot tell which host process wrote them. Define a daemon identity: a stable id per daemon instance (declared in the launch environment beside APPROVAL_HUMAN, or derived from the keystore instance id doctor already prints as keychain-scope), carried on every daemon-written record in a field the schema names, and printed by approval status and doctor. A tenant policy may then name which daemon ids may act (a hosts allowlist next to senders), refusing records from an unlisted one at the write boundary. Keep it to identity and allowlist: multi-tenant process isolation, token scoping and billing are separate tasks. Related: APRV-324, APRV-356, APRV-382, the keychain-scope doctor row, SPEC 11.1 invariant that self-reported fields never reduce scrutiny (an unlisted host is refused, a listed one gains nothing).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
SHIPPED AND WIRED. All four criteria have evidence; the schema change is called out below because this task IS the schema task for it.

THE FIELD AND THE KEY, NAMED. The record field is a new optional TOP-LEVEL field called daemon, beside actor. The policy key is a new top-level array called daemons. Both are additive and optional, so every record and every policy written before them validates and verifies unchanged, which is AC2 second half.

WHY daemon AND NOT A PAYLOAD FIELD. actor says who caused an event; daemon says which process wrote it down. Being top level means the record hash covers it exactly as it covers actor, and a provenance field the chain did not cover could be edited in place without breaking anything. tests/daemon-identity.test.ts asserts that mutating the field invalidates the digest. It reaches no payload hash and no token, which is the line SPEC 11.1 invariant 4 draws.

WHY daemons AND NOT A MEMBER OF THE EXISTING daemon BLOCK. The singular block from APRV-217 is documented as latency settings whose strictest value is the default. The plural key is ENFORCEMENT. Putting it inside would leave one sentence that is true of five keys and false of the sixth, and an absent-means-default reading next to an absent-means-no-restriction one. The closest precedent for the shape is audit.checkpoint_keys, also a list of who may do something, also read from the attested policy, also refusing what it does not name. Both schema descriptions now cross-reference the other so a reader meeting daemon and daemons together is told the difference.

THE ID DERIVATION, WHICH IS AC1. APPROVAL_DAEMON_ID from the launch environment wins; otherwise the id derives as daemon- plus the eight hex digits core/instance.ts already computes from the absolute path of the instance .approval directory. That is deliberately the SAME id doctor prints as its keychain-scope suffix, so an operator comparing daemon-3f2a9c11 in a record against approval-tg-token-3f2a9c11 in their env file is looking at one gate. Nothing is stored, so stability across restarts follows from the input being a path. Rejected: a random id in a file (a file an operator can copy is an identity that travels, which is the bug core/instance.ts documents) and a per-process id (it would make the allowlist unwritable).

A DECLARED ID THAT FAILS THE GRAMMAR IS A REFUSAL, NEVER A FALL BACK. The operator meant the value they set; substituting the derived one would write records under a name nobody chose and check them against a list nobody wrote for it. approval up and approval daemon run resolve before constructing the Daemon and exit 2, because a process whose whole purpose is writing should not start to find out it cannot. The Daemon constructor declares the identity anyway, as an identity with NO id, which refuses every append at the write boundary; that is what covers a Daemon an embedder or a test builds directly.

TWO MODULES, AND THE SECOND REASON IS AN IMPORT CYCLE. core/daemon-identity.ts is a leaf (it imports core/daemon-actor.ts and nothing else): grammar, process state, and the one question the write boundary asks. core/daemon-host.ts does the reading: environment, instance, attested policy. The seam is right on its own terms, and it is also forced: core/instance.ts reaches core/attest.ts through core/env-file.ts, and core/attest.ts spreads APPEND_ERROR_CODES at module scope, so importing the derivation into core/log.ts would close a cycle that throws on evaluation before any test runs. Discovered by reasoning about the graph rather than by a crash, and stated in both module headers.

THE STATE IS MODULE STATE, ARGUMENT-FREE IN THE SAME SENSE core/daemon-actor.ts IS. EventInput gained NO daemon member, so there is no spelling of an append option by which a session can claim to be a daemon. buildRecord composes a record field by field rather than spreading the input, so a caller that puts the property on its input object anyway is ignored; a test pins exactly that, through the real append path.

THE ALLOWLIST RULE, IN ONE SENTENCE. The restriction in force is the one from the most recent SUCCESSFUL resolution of the attested policy. A resolution that fails (unloadable, or not attested) sets nothing, so the previous restriction stands and a policy that becomes unreadable under a running daemon is not a way out of the list it carried a moment ago. The asymmetry that falls out is the right one: narrowing takes effect on the next tick, widening past an unreadable policy takes a restart. A run whose policy was never attested is unrestricted, which is what every run before this key looked like, and is the one place this mechanism is honestly weak: it defends against a misconfigured daemon rather than against a host that controls the policy file. The design note says so in section 6.1 rather than leaving a reader to infer a guarantee that is not there.

REFUSED BEFORE THE LOCK, NOT INSIDE IT. appendEvent asks daemonStampForAppend() before taking the append lock, because the question reads no log state and taking a lock only to refuse makes every other writer wait for an answer that was never going to touch the file. One observed consequence worth knowing: a refused append does not even CREATE the log file when none existed, which a test asserts. The schema pins the field shape independently, so a malformed id could not land even if this check were absent.

TWO CODES, NOT ONE, ON THE FROZEN UNION. daemon-id-invalid (the launch environment is broken; no record could be attributed to anything) and daemon-not-allowed (the attested list does not admit this daemon). The repairs have nothing in common, and a caller that could not tell them apart would send an operator hunting through a policy for a broken variable. Both are spread into APPEND_ERROR_CODES from core/daemon-identity.ts so the codes and the logic that emits them cannot drift; refusal-unions vectors take a MAJOR bump to 21.0.0 (the suite pins each union whole, in definition order) and schema-validation a MINOR to 2.7.0 (five new fixtures, no expectation moved).

WHAT I FOUND WHILE TESTING, AND IT IS NOT IN THE BRIEF. THE ALLOWLIST GOVERNS THE LOG AND NOTHING ELSE. A refused daemon still reads, still renders QUEUE.md and still repairs a task file state: line to match the log, because none of those is an append. So a host whose id a tenant has removed can still write in the tenant working tree until somebody stops the process. Observed in the unlisted-daemon test, which shows a write_back line and no drift record in the same pass. Recorded in the design note section 6.2 rather than left for somebody to discover: confining the filesystem is process isolation, which is explicitly out of scope.

THE DOCTOR ROW IS A SKIP AND NOT A FAIL FOR AN UNLISTED ID, WHICH IS A JUDGEMENT CALL. Under the deployment this key exists FOR, the tenant policy names a daemon id belonging to somebody else machine, so a fail would be red on every tenant laptop forever, and a red row on every installation is a red row people learn to skip past. That is keychain-scope own stated reason for treating the legacy item as a skip. The row DOES fail for an unusable APPROVAL_DAEMON_ID in the shell, which is broken wherever it is read.

THE STARTED LINE AND status. The daemon started line gained a daemon field and its human sentence now opens with the id, beside the read proof, the anchor and the draw socket, for the reason those are there. approval status reports daemon: {id, source, allowed}, ALWAYS present (the coverage precedent), because status is not the daemon and the fact it reports is the id a daemon started HERE would write: what an operator needs before anything is running, and what a tenant needs to look up a daemon field they have just read. The verb registry output schema grew the key, which is what the registry conformance test validates against.

INVARIANTS TOUCHED, SPEC section 11.1. Invariant 4 (self-reported fields never reduce scrutiny) is the one this task is ABOUT: the id is self-reported, a listed id gains nothing anywhere in the runtime, an unlisted one is refused, and no verdict, autonomy, budget, floor, sampling draw, token or TTL reads the field or the list. Invariant 1 (enforcement reads only verified records): the allowlist is resolved from the caller own verified read plus its own attestation check, never from a claim. Invariant 6 (refusals machine-readable and distinct): two new members on a frozen union, pinned by tests/log.test.ts and by the conformance vectors. Fail closed: an unusable declared id refuses rather than substituting, and a failed allowlist resolution leaves the previous restriction standing. Invariant 7 (no implicit working-tree configuration): the id comes from the launch environment or from a path, never from a file in the tree. Invariant 5 and invariant 8 are untouched; nothing about the compare-and-append path or the verdict-then-append ordering moved.

SPEC HUNKS PROPOSED, NOT APPLIED, and both are in design/hosted-daemon-identity.md section 7 in full: one new bullet in section 8 record fields for the daemon field, and two rows in the section 11.2 append_error_codes table. A third possible hunk (a sentence in section 5.2 naming daemons beside approvers) is deliberately NOT proposed and the note says why: section 5.2 does not enumerate every key, and a human who wants the vocabulary complete there should ask rather than have this task assume it. ## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Daemon-written records now name the daemon that wrote them, and an attested policy may list which daemon ids may write at all.

A new optional top-level record field, daemon, carries the writing daemon instance id: APPROVAL_DAEMON_ID from the launch environment where set, otherwise daemon- plus the instance id doctor prints as keychain-scope, so it is stable across restarts on one machine and keystore with nothing stored. It is stamped by the writing process (core/daemon-identity.ts holds the state, argument-free like core/daemon-actor.ts) and can never be supplied by a caller, since EventInput has no such member. A new top-level policy array, daemons, is an allowlist read only from the attested policy: absent means no restriction, and an unlisted id is refused at the write boundary with daemon-not-allowed while an unusable declared id is refused with daemon-id-invalid, both new members of the frozen append union. The id is printed on the daemon started line, by approval status as daemon: {id, source, allowed}, and by a new doctor row daemon-identity. design/hosted-daemon-identity.md states the four properties of the hosting model and names what is out of scope (process isolation, token scoping, billing) plus the one thing found while testing: the allowlist governs the log and not the filesystem.

Verified: build, typecheck, lint exit 0; new tests/daemon-identity.test.ts 15 pass exercising stamp and both refusals through the REAL append path; five new end-to-end cases in tests/daemon.test.ts (42 pass); node conformance/run.mjs 458 of 458 with the regenerated manifest (refusal-unions major 21.0.0, schema-validation minor 2.7.0); full npm test 5024 tests, 5001 pass, 22 fail, exit 1, all 22 the known SMTP baseline on Node 26. Two SPEC hunks are proposed in the design note section 7 and no SPEC sentence was edited.
