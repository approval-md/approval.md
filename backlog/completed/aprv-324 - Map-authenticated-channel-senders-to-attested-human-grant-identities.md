## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
GitHub issue #137 requests grant attribution to the actual Telegram callback sender rather than the shared listener process identity. Design an operator-attested sender-to-human mapping inside the existing machine trust boundary, coordinated with APRV249, without treating caller-supplied identity as proof.
<!-- SECTION:DESCRIPTION:END -->

Section 3 defines the mapping: an additive optional senders key inside the existing approvers roster in APPROVAL.md, so it inherits the human-only attestation ceremony that already protects the roster and an agent cannot add itself as an approver's sender. It is written person to sender, per channel, and resolved at the channel boundary before decide is called, so the gate's authorization logic including namesApprover and actor-not-approver is completely unchanged. Section 3.3 makes an unmapped sender a refusal recorded as an audit.decision_refused with a new sender-unmapped code carrying the observed id, explicitly NOT a fallback to the configured actor, because that is today's behaviour dressed up as a feature and would still let a stranger in the chat approve as Carter. Section 4 specifies the audit fields: set the channel field the base schema already defines and the grant never sets; add payload.sender and payload.sender_source, both optional and additive, so the ABSENCE of sender is itself meaningful and says the attribution came from configuration. It also says what must never be recorded: from.username, because it is mutable and reusable and a log carrying it grows a field that reads like identity and decays into a lie, and anything the sender claims about themselves, which is the self-reported-fields invariant.

Section 6 is the safe migration: phase 1 records the sender without enforcing, so the operator learns from their own log which ids have been deciding and therefore what to write in the policy; phase 2 maps and warns; phase 3 refuses, gated on a clean doctor row so nobody arrives there by accident. Rollback is removing the key at the next attestation, with no code change and no log repair, which is the argument for the mapping living in policy rather than a separate store. A deployment that never adopts it is byte-identical to today, and that is the first test in section 7.

One finding worth Carter's attention independently of this design. SPEC.md section 10.3 at line 460 describes Telegram as callback verified against approver identity. That is not what the code does: the callback is verified against a configured chat id and no approver identity is read from it. SPEC 11 line 549 and SPEC 5.2 line 137 are both precise and correct, so this is a local imprecision rather than a contradiction of the model, but it is exactly the sentence a reader would rely on. What the runtime does now. src/core/sender-identity.ts is the whole of the decision-time logic: pure, total, no I/O, four resolution modes. src/channels/telegram.ts reads callback_query.from.id in routeCallback, after the configured chat check and before any decision is assembled, and reports it on the gesture; nothing in the message, the callback data or the username is read. src/channels/contract.ts resolves that observation against the attested policy BEFORE calling decide, so the gate's authorization logic is untouched and namesApprover still refuses actor-not-approver with no new path. src/core/gate.ts records payload.sender, payload.sender_source and the top-level channel field on the decision record; the event schema constrains all three at the write boundary.

Decision where the design was impractical as written. Section 3.2 says the sender rides on ChannelActorOptions. It rides on ChannelDecision instead: onDecision registers ONE handler per listener process and the actor options are built from fixed setup data, so a per-listener field cannot carry a per-gesture fact, and giving each channel a mutable slot to stash it in would be the channel-held state section 10.3 forbids.

Decision where the design was silent. Mode 1 is keyed on the POLICY rather than on the transport: a supplied sender with no senders block for that channel is today's configured attribution, because a channel that starts supplying senders would otherwise lock every existing installation out of its own gate at the first upgrade. Writing the first entry for a channel is what turns enforcement on for it. A policy that does NOT load is not a policy with no mapping and fails closed: a supplied sender is refused sender-unmapped rather than attributed. Nothing is stranded by that, because the CLI channel supplies no sender, so a terminal can always decide and always repair the file, which is where a policy.core edit has to happen anyway.

Decision on section 7 tests 1 and 18, which contradict each other. Test 1 asks for a log byte-identical to today under a policy with no senders; test 18 asks that every decision record carry channel, which section 4 item 1 states outright and calls worth doing on its own merits. The channel field wins and test 1 is implemented as the attribution claim it is: same actor, same decision, same payload keys, neither new key present, on all three channels. The structural fix. senderOf is read once, directly after the chat-id check, above every branch. That placement is the point: read later, each family is another chance for one of them to keep the old behaviour, and a new branch written next year would inherit the gap by default.

Family by family. Checkpoint signatures: resolved exactly as a decision, mapped signs as the mapped human, unmapped refuses and signs nothing, no mapping is today's behaviour. The signed payload gains no sender field, deliberately, because an unsigned field beside a signature reads to a later reader as covered by one; what the mapping moves here is the actor, which is what the signature is over. Reviews, including the note-reply path: resolved the same way, and audit.reviewed gains payload.sender on the same additive terms as a decision. The ForceReply note prompt now remembers which account armed it, and a reply from a different account records nothing and leaves the prompt open, because the prompt is addressed to the person who tapped and its words are recorded as theirs.

Attestation answers, the one that is stricter rather than the same. The amendment a tap attests can itself add, remove or repoint the mapping, so resolving against the file being attested would let whoever wrote that file name the account that approves their own edit. The oracle is the policy IN FORCE. Ladder: no sender is unchanged, which is what keeps the repository repairable; in-force bytes recovered and the mapping changed means only an account the IN-FORCE policy maps may answer, and where it maps nobody the answer is the new code attest-requires-terminal; in-force bytes recovered and the mapping unchanged is the ordinary rule run against the policy in force; in-force bytes not recovered refuses attest-requires-terminal whenever the proposed policy maps senders for the channel, and is otherwise today's behaviour.

Evidence on whether the in-force bytes can be obtained, which the review asked for. They can, sometimes, and the implementation does it: every policy.proposed binds the whole policy text into the payload store per SPEC 10.4, so a proposal that was attested left the attested text addressable by its own payload_hash. inForcePolicyText finds the hash in force, finds a proposal naming exactly those bytes, reads the stored text and re-hashes it against the attested digest, so nothing trusts the store and a tampered payload is a recovery failure rather than a different policy wearing the attested hash. It fails in the ordinary case and says so: approval policy attest, and policy amend on its human path, append a policy.updated and store nothing, so a chain never amended from a phone has no recoverable bytes at all. That is this repository's own state, which makes the fourth rung the common path and not a corner. Both halves are implemented, so a phone-attested chain gets the stronger property and everyone else gets the fail-closed one.

The residual, stated rather than hidden. On the fourth rung an amendment that REMOVES a mapping is indistinguishable from a policy that never had one, so it falls back to the pre-mapping behaviour. Closing it needs the in-force bytes, which is the second rung. Reaching it requires an attacker who can already write APPROVAL.md, whom SPEC section 11 already places inside the trust boundary.

That is the false record this task exists to remove, and a new audit event type is a schema task of its own per CLAUDE.md. Second follow-up, 2026-09-17, after the orchestrator's re-review and an independent verification pass.

The fix that was asked for. Checkpoint and review taps resolved through the policy file ON DISK whether or not it was attested. A decision is protected afterwards because decide refuses policy-not-attested or policy-drift, but signing and reviewing read the policy, act and append with nothing behind them, so an edited APPROVAL.md that dropped or repointed the senders block would have changed who may sign a checkpoint or file a review from a phone before any human attested it. That is exactly the property the module header and SPEC 5.2 claim the mapping does not have. Now: when a gesture carries a sender, the on-disk policy is checked with core/attest.ts's own checkAttestation and its own attestationRefusal wording, not a second comparison, and anything but attested refuses with the gate's existing policy-not-attested code, records nothing, and says in the terminal line and the chat line that a terminal can still do it. With no sender the behaviour is unchanged.

Worth knowing, because it is broader than it sounds: the Bot API always sends a from object, so on Telegram a sender is effectively always present and this check therefore applies to every phone signature and review, mapped or not. That is the stricter reading and I kept it. It costs an operator whose policy is unattested the ability to sign or review from the phone, which is a state in which nothing could be approved either, and the terminal is unaffected.

A fixture correction fell out of it. tests/checkpoint-tap.test.ts grew its log by attesting a throwaway marker file, which left APPROVAL.md permanently unattested, a shape no deployment has. It now attests its own policy, so the fixture exercises the real path.
