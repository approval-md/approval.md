## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Codex can run under an approval policy where, before executing a command or applying a patch, it stops and asks its client for a decision over the app-server protocol (https://learn.chatgpt.com/docs/app-server); the harness waits for the answer and runs nothing until it arrives. If approval.md answers as that client, the interception is fail-closed by construction (no answer means no execution), which is exactly what the native hook lacks (APRV-311: no per-call cwd, no outcome, fails open). APRV-325 named this bridge as a candidate beside the constrained-session-plus-executor route and chose the executor without probing the bridge live; the broker (APRV-325.2, PR #406) and confinement (APRV-325.3) remain the mandatory-boundary answer, and this spike asks whether the app-server route can give native shell and patch the same class-and-policy gate Claude Code gets from its hook, so everyday Codex use is gated rather than confined. Bounded, isolated, read-only probes against the installed Codex CLI in scratch directories only: never the host ~/.codex, never the primary checkout, never a real credential. Questions to settle with evidence: (1) what the exec and patch approval requests carry (command bytes, cwd, patch content, call id) and whether they bind enough for the classifier and the guard; (2) what happens on client crash, disconnect, timeout and malformed reply (observed file effects and exit codes, reported as observed); (3) whether the model can answer its own approval or route around the client (native approval impersonation, APRV-325 AC3); (4) how a decision reaches the phone and the log from the client (register, request, wait, then answer), and what the per-call latency is; (5) whether the bridge composes with the read-only sandbox and the broker or replaces them for everyday sessions. Output is a design note under docs/ with the probe scripts under scripts/probes/, and a recommendation: adopt (with the follow-up tasks it needs), or decline with the failing evidence. Related: APRV-311, APRV-325, APRV-325.2, APRV-325.3, APRV-348.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Source reading done by a Sonnet subagent against openai/codex at commit b0659c53865dd48b0cd69c454368cea3980017cc, with a file and line for every claim; docs/codex-app-server-bridge.md carries the citations. Cross-checked against the INSTALLED 0.152.1 binary by reading its string table with grep (the binary was never executed): the request method names item/commandExecution/requestApproval, item/fileChange/requestApproval and the legacy execCommandApproval and applyPatchApproval are all present in the shipped release, so the source read describes the protocol the operator will actually speak.

Findings in order of how much they move the answer. One, the exec approval request carries both the command and its cwd on the same frame, minted by the runtime rather than reported by the model. That is exactly the pair the native hook cannot get and the reason APRV-311 refuses every native shell call. Two, the item-based file-change approval request carries NO patch content at all, only an item identifier and a grant root; the content arrived earlier on a different notification, so a client on that API approves a reference rather than bytes. The legacy patch request does carry the changes map inline. Three, there is no timeout anywhere on the approval await, in core or in the app server, so silence blocks rather than releases; a malformed reply or an unknown decision value deserializes to a denial with a fixed rejection string, and the decision type's own default is denied. Four, a disconnected client leaves the question pending and the thread running, and a reconnect REPLAYS the pending request to whatever connects next, so the property is that this client decided every question it was asked, which is narrower than every question was decided here. Five, and this is what caps the recommendation: a server-side auto-reviewer runs BEFORE the client path and can resolve an approval with a model call, telling the client afterwards through a notification rather than through the approval channel. The acting model cannot answer its own request (the notify path is not exposed as a tool), but a model upstream of the client can, and whether it runs is harness configuration this project does not attest.

Deliverables. scripts/probes/codex-app-server.mjs, dependency free, three modes. Setup builds a scratch workspace of synthetic files under a directory made with fs.mkdtemp plus a pointer file under the system temp root. Run resolves the harness binary from PATH, prints its version, checks authentication first and stops cleanly with sysexits 69 if there is none, then drives five trials (approve, deny, client crash mid request, no reply until the deadline, malformed reply), each in its own workspace, each asking for one harmless command and one harmless patch. Report prints per approval kind the union of parameter key paths with presence lines for the directory, a call id, command bytes, patch content and a reason, then the count of auto-review notifications, then one row per trial saying whether each effect happened. It reads no credential, never touches the harness home, redacts token-shaped strings and blanks any value under a secret-shaped key before recording a frame, and it answers in the vocabulary the request advertises rather than in an enum pinned in this file.

tests/probe-codex-app-server.test.ts drives all of that against a stub server written in the test, so the script the operator runs once has already been run. Five cases, 5 pass, 0 fail, exit 0. One of them exists to stop the design note being written the wrong way round: a second stub performs the effect BEFORE the answer arrives, and the report must call that a failure to block in those words and must not be able to present it as enforcement.

Two design choices worth review. The probe answers only accept and decline, never acceptForSession (standing authority for a whole session is a grant shape this project does not have) and never cancel or abort (those mean stop the turn, and recording an interruption as a denial would be a lie in the log). And where the probe must send something whose shape it cannot know, it tries a ladder of candidate parameter shapes and records every refusal, so a moved field appears in the report as a moved field instead of as a crash.

No acceptance criterion is checked, and each one is unchecked for its own reason rather than for a shared one.

Criterion one and criterion two are observation criteria and the observation has not happened. The probe drives a real harness in app-server mode, which needs the operator's login and is a billable model call, so no agent session may make it: that is runbook step 2 at private/runbook-2026-09-17.md, three commands (setup, run, report), and the pasted report is what checks them. What exists today is the script, exercised end to end in CI against a stub, and a design note whose question-two answers are each marked source with a file, line and commit rather than observed.

Criterion three is unchecked on one clause. docs/codex-app-server-bridge.md answers all five questions, states what the bridge could and could not bind, walks a decision through register, request, wait and answer with the latency that implies, says how it composes with the sandbox and the broker, and ends in a recommendation that names eight follow-up tasks. The clause it does not yet satisfy is the description's own wording for question two, observed file effects and exit codes: those columns say observed (pending) today. Closing it is an edit of that one section after the report is pasted, not new work.

Criterion four cannot be evaluated before the run, and reading it carefully turned up something worth the operator's attention rather than my silent judgement. Its first clause is already true of this lane: nothing here touched a harness home, a credential, the primary checkout or a production policy, and the probe is written so a run cannot either. Its second clause says every command the probe runs is one the classifier reads or one routed through approval run. The command the OPERATOR types classifies cleanly: approval hook classify on the probe invocation returns files.write.workspace by the node-script rule. The subprocess the probe then spawns does not: approval hook classify on the harness binary in app-server mode returns unclassified, no rule, which is the fail-closed default and the same refusal APRV-311 recorded for the version check. So the literal reading of that clause is not satisfied by any probe that starts this harness at all. Two ways out, and the choice is the operator's: add a classifier rule for the harness binary in app-server mode, or accept that this probe is an operator-run command from a runbook, which is the path APRV-310 and APRV-325 both used for exactly this reason. Recording it rather than quietly checking the box.

From Lane A (APRV-354), so this is on the record where AC4 will be checked: `codex app-server` is no longer a command the classifier cannot read. As of APRV-354 it classifies harness.launch.codex, rule harness-launch-codex, with app-server bound as the argv, and the same holds for the absolute-path, home-relative, env-prefixed and package-runner spellings, so a probe that spawns it is spawning something the classifier reads rather than something that reaches hook-unclassified. A version probe (codex --version, -V, --help, -h, or a lone help as the whole argv) classifies read.shell with rule harness-probe, so the probe can read the installed version without a prompt. AC4 wording is therefore satisfiable on the classifier side once APRV-354 merges.

Two things this does NOT do, and the probe still has to. First, the class is manual in the reference proposal and human-only for Muse, so a spawn reaches the gate rather than proceeding: the probe will need a grant, or a policy of its own in its scratch instance. Second, a grant of harness.launch.codex covers the LAUNCH and nothing the launched session then does, which is the laundering boundary SPEC 7 now states; the probe report should not read a granted launch as a gated inner session. The confined approval codex start keeps gate.self and is not a launch.
