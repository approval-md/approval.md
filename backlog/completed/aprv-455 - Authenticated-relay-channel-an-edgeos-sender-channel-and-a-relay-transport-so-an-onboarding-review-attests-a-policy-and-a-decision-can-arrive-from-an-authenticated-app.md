## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Agent Village residents review their approval.md settings in the Edge City onboarding app, and Carter wants that review to be the attestation of the policy in force (and later changes to it). Core admits only telegram under approvers.<id>.senders (schema/policy.schema.json line 419: a channel whose transport attributes a gesture to an account id the sender cannot choose; web and cli deliberately absent), the web channel is loopback and unauthenticated, and grant, reject and attest are human-only verbs absent from approval serve. An EdgeOS-authenticated session in the control plane attributes an acceptance to a stable human id (the EdgeOS /humans/me id) the resident cannot choose, under the same operator trust the Telegram relay already asks for (the daemon trusts the relay's report of callback_query.from.id). Design and build: (1) a new sender channel name, edgeos, mapped beside telegram in approvers.<id>.senders, with the schema rationale extended on the APRV-324 ground; (2) a relay transport the daemon process runs (a sibling of channel telegram webhook): an inbound POST authenticated by a shared secret from the launch environment, carrying a gesture (attest a proposed policy by hash, or grant/reject a request by id), the sender id, and the hash the human saw; mapped against the attested policy's senders exactly as a Telegram tap is; refused sender-unmapped and audited otherwise; a forged post appends nothing; (3) the attestation case: the control plane proposes the rendered policy (policy.proposed with the semantic diff, as the channel attestation path APRV-109 already does) and the resident's acceptance in the app appends policy.updated with actor human:<resident> and payload.sender {channel: edgeos, id}; the operator bootstrap attestation (APRV-449) is what makes the resident a mapped sender the first time; (4) SPEC section 10.3 hunk proposed as pending sign-off, stating the trust level in APRV-422's words. Never an HTTP decision verb on serve's agent or tenant credentials: this is a third transport with its own secret, in the daemon's process. Context: approval-md private/agentvillage-integration/05-integration-architecture.md section 5 (gitignored pack).

Implementation notes (APRV-455).

WHAT WAS DONE. Part 1: schema `senderChannel` enum [telegram, edgeos] with the rationale extended on the APRV-324 ground; `senders.edgeos` raw grammar ^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$ (opaque /humans/me id, colon-free so it never reads as the keyed form and never contains the sender-index separator) or keyed hmac-sha256:<hex>. `sender-identity.ts`: SENDER_CHANNELS gains edgeos, EDGEOS_SENDER_ID_PATTERN/isEdgeosSenderId, and resolveSender never compares an observed id wearing the keyed prefix raw (no effect on Telegram, whose ids are digits). Part 2: `approval channel relay` (src/cli/channel-relay.ts), protocol src/channels/relay.ts, HTTP src/channels/relay-server.ts; `ChannelActorOptions.requireSenderMapping` in contract.ts; `ProposeInput.reaffirm` in policy-proposal.ts; Telegram terminalDeliveries now settles a proposal by the LATEST proposal under its key; registry entry human_only; conformance union relay_refusal_codes (refusal-unions 26.0.0).

DECISIONS. (1) One PR, one commit (the two-PR split was optional; one queue pass avoids a CHANGELOG re-merge). (2) Verb name `approval channel relay`, beside `channel telegram webhook`: it is a channel arrival, and the lane table named it. (3) The secret is the conventional APPROVAL_RELAY_SECRET (24+ chars of A-Za-z0-9_-), not a policy-declared secret_env, for APPROVAL_TG_WEBHOOK_SECRET's reason and to keep the schema hunk to `senders` only. (4) Body field is `action_key`, not `request_id`: requests are keyed by action key in this runtime and that is what a Telegram tap routes on. (5) `decline` added beside attest so the app can refuse a proposal. (6) The relay holds no human identity: requireSenderMapping turns every configured-actor fallback into sender-unmapped + one audit.decision_refused, on decisions and on every rung of the attestation ladder. (7) Every relay gesture resolves its sender against the policy IN FORCE (inForcePolicyText, hash-verified), never the file on disk; unrecoverable in-force bytes refuse policy-not-attested and append nothing (refuter H1). (8) `propose` is a relay gesture (the existing route, `policy amend`, is a git-aware blocking terminal ceremony): it re-hashes the file and refuses relay-policy-mismatch for bytes the caller did not render, diffs against the verified in-force text, is idempotent on retry, records under an agent: proposer only (default agent:edgeos-relay), and sets wait_until one hour out. (9) Reaffirm: a relay proposal may name bytes already in force, so an unchanged onboarding review still makes the resident the attester of record; `policy amend` keeps refusing policy-already-attested. Drift is keyed on the hash, so a reaffirmation voids no pending request. (10) Replay: nonce (16-128 of A-Za-z0-9_-) plus issued_at (RFC 3339 UTC, five-minute window, never recorded); nonces claimed by writing a temp and hard-linking it into .approval/daemon/relay-nonces/<sha256(nonce)> (EEXIST = replay), retained 11 minutes, so replay is refused across restarts and across two relays without a transport lease. (11) A grant's raw token is dropped unread; the response says token_issued only. (12) Attestation records carry no top-level channel (decideAttestation never set one, for Telegram either); payload.sender.channel = edgeos is the surface marker. (13) Transport refusals use {error:{code}} with 4xx/5xx and append nothing; gate and surface refusals come back 409 {refusal:{code}} from their own unions.

GLOBAL INVARIANTS TOUCHED (SPEC 11.1). Verified records only: sender resolution reads the in-force text via readVerifiedRecords + hash check. No caller timestamps: issued_at is a refusal input only, every ts is the runtime's tick. Raw secrets never in the log: the relay secret appears nowhere (tested over log, payload store, responses, operational lines) and the raw execution token is dropped. Self-reported fields never reduce scrutiny: issued_at, nonce and the body can only cause refusals; the sender id is resolved against the attested mapping. Compare-and-append: proposals and decisions use the existing append paths with an expected head. Refusals distinct: new frozen unions RELAY_REFUSAL_CODES (conformance) and RELAY_START_REFUSAL_CODES (pinned in tests/channel-relay.test.ts). Human-only classes: unchanged, class-human-only still refuses.

REFUTER (opus, on HEAD 5d78a3cf). No BLOCKER. Fixed: H1 decisions resolved against an unattested on-disk mapping (pre-existing on the Telegram path since APRV-324; fixed for the relay under requireSenderMapping, Telegram unchanged; follow-up candidate for the Telegram listener); M1 prune could delete a claim file another relay had created but not yet written (now written whole and linked into place; prune judges non-time content by mtime); M2 Telegram settled a second proposal of one hash by the first proposal's answer (now the latest); L1 human: proposer refused; L2 relay proposals now expire after an hour, and decline semantics are documented (it leaves the attestation in force); L3 leak test now covers responses and operational lines, import scan is recursive, H1 and M1 have regression tests. Open for a human: M3 the secret is a bearer header to a loopback port inside a multi-uid sandbox, so the control plane must check the listener belongs to approvald before posting (documented); a unix socket or an HMAC body signature would remove that check and is not in this version. N1 the schema change ships in the feature commit ahead of the SPEC sign-off, as the brief asked.

RESIDUALS. A manual-delivery request granted through the relay has a token nobody holds (requester asks again). While a proposal's bytes sit unattested on disk every gated call refuses policy-not-attested, so the control plane must propose and collect the acceptance in one screen and restore the in-force bytes on decline or lapse. A clock step of more than 11 minutes could prune live nonce files.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->

New frozen union relay_refusal_codes. Verified by tests/channel-relay.test.ts against a fake control plane, tests/sender-edgeos.test.ts, the full suite (exit 0) and an opus refuter whose H1/M1/M2/L1-L3 findings were fixed; SPEC 5.2/10.3/11.2 hunks proposed in the notes pending sign-off (APRV-454 batch).
