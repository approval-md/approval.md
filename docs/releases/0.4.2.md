# approval-md 0.4.2: release notes for downstream

The changelog section `## 0.4.2 — 2026-10-06` in [`CHANGELOG.md`](../../CHANGELOG.md)
is the authoritative list of changes and becomes the GitHub Release body when
the tag is published (`scripts/release-notes.mjs`, APRV-396). This page is the
companion for the downstream projects that pin this runtime: what 0.4.2 changes
for a resident and for an operator, the order in which pins and policy keys
move, the conformance versions, and the `SPEC.md` amendments this release
proposes (APRV-501).

Until the tag `v0.4.2` exists and the Trusted Publishing run has finished,
`approval-md@0.4.2` is a version this source tree carries and nothing more. The
tag and its push are gated `release.publish` acts, so check the registry
(`npm view approval-md@0.4.2 version`) before baking the string anywhere.

## What changes for a resident

- **Every app's tool calls can be recorded (APRV-499, #623).** Until 0.4.2 a
  tool call the harness adapter's own tables did not know (every MCP tool, so
  every marketplace app, and tools such as Claude Code's `WebFetch` or a
  Hermes `web_search`) was allowed as "not a gated tool" and left no record.
  A policy can now name the class each tool is judged under (`tools`) and say
  what happens to a tool nothing names (`defaults.unmapped_tool: record` or
  `ask`). Under `record` the call goes ahead and the log says it happened;
  under `ask` it comes to the resident's phone like any manual action. A new
  app is a policy line, not a runtime release.
- **Nothing a model says is a person's decision (APRV-500, #624).** The
  `model:` identity is reserved for a later judge and admitted only in the
  policy's reviewer list. Every approval, review, attestation and channel tap
  still needs a `human:` identity, and a `human:` id dressed as a model
  (`human:model:...`) is refused as not a person.

## What changes for an operator

- **Tool-name mapping (APRV-499).** `tools` is an ordered list of
  `{match, class}`; `match` is a glob over the whole tool name (`*` is the only
  wildcard), `class` must be declared by `classes` (exact key or under a
  trailing `<prefix>.*` family), and the first match wins. The adapter's shell,
  file, read and pass-through tools and Hermes's rule table keep precedence
  over every entry. `defaults.unmapped_tool` covers what no entry claims:
  `record` judges the call under `harness.tool.unmapped` (resolves
  `autonomous` unless a `classes` rule says otherwise, and writes an
  `execution.started` carrying `payload.harness_tool`), `ask` resolves it
  `manual`. Absent, nothing changes. A malformed entry or an undeclared class
  fails the whole policy closed. Details: `docs/claude-code-hook.md` (including
  the matcher an MCP tool needs to reach the hook) and `docs/hermes-hook.md`.
- **Behaviour changes to plan for.**
  - Under a policy that does not load, a tool the adapter does not know is now
    refused `hook-policy-unavailable`, where it was allowed. The refusal lists
    the first entries at fault and the repair.
  - Under an edited or never-attested policy, such a tool is refused
    `hook-gate-refused:policy-not-attested`, as `Bash` is: deleting a `tools`
    line on disk loosens nothing until a human attests the edit. Re-attesting
    restores the old answer.
  - Under an attested policy that declares neither key, the answer is
    unchanged, at the cost of one policy read and one verified log read per
    such call.
  - `harness.tool.unmapped` is reserved to the harness hook: a task envelope,
    `approval propose`, an HTTP registration or a token-minting
    `approval request` declaring it is refused `envelope-invalid`, and
    `approval run` / `approval consume` refuse a grant under it
    (`harness-executed`).
- **Known property, not a fix (ruling H1).** Under
  `defaults.unmapped_tool: record`, every unmapped harness tool call is exempt
  from every global `daily_actions` budget and from the loop floor's streaks.
  Class-scoped `limits` on `harness.tool.unmapped` and every `daily_usd`
  budget still meter it. A record-only start is one the hook writes under
  `record` with no human grant; a granted (`ask`) call counts as before,
  including a spend whose grant is older than the 24 h window. The village
  template sets no class limit on `harness.tool.unmapped` for now (every Index
  tool is mapped by name; a cap belongs in the app install flow when the
  marketplace opens). An operator who wants `daily_actions` as a backstop over
  unmapped calls declares a class limit on `harness.tool.unmapped`, or maps the
  tools to classes of its own.
- **The `delegation` block (APRV-500).** Reserved, validated and inert. It
  loads only in its off form (`delegation: {}`, or every key at `model: null`,
  `classes: []`, `max_autonomy: manual`, `daily_cap: 0`, `escalate_on: []`,
  `advice: false`, `reviewers: []`) and then changes nothing. Any other value
  fails the policy closed with the new load code `delegation-not-supported`,
  so every class resolves `manual`; a block that also breaks one of its
  relationship rules (exact class keys, no `human-only` or `autonomous` class,
  the `max_autonomy` pin, escalation floors, reviewer identities) fails
  `schema-invalid` first. `approval policy check` notes a declared block and
  `approval policy diff` shows its `delegation.<key>` paths. A bare
  `delegation:` (YAML null) is `schema-invalid`: emit `delegation: {}` or omit
  the key. Reference: `docs/cli-reference.md`, "Delegation block, reserved in
  0.4.2; no behaviour".

## Upgrade order

**Every pin on 0.4.2 before any policy carries `tools`,
`defaults.unmapped_tool` or `delegation`.** The policy schema is closed. On
0.4.1 and every earlier core those keys (even `delegation: {}`) are
`schema-invalid`, and the whole policy fails closed to all-`manual`: every
resident's every gated call would go to the phone. So:

1. Publish 0.4.2 and read it back (`npm view approval-md@0.4.2 version`).
2. Move every runtime that reads the policy (the harness hook and the daemon,
   on every tenant) to 0.4.2: the checkpoint rebake and the hosted pin below.
3. Only then may the control plane's resident template write `tools`,
   `defaults.unmapped_tool` or `delegation`.

| downstream | where | move to | owner |
|---|---|---|---|
| agentvillage-data | the checkpoint install `APPROVALD_BIN` points at, and the version the launcher bakes | `approval-md@0.4.2` from npm, once published | DATA-228 |
| approval-md-hosted | root `Dockerfile` pin of approval-md core | tag `v0.4.2` | HOSTED-32 |

Neither pin moves before `npm view approval-md@0.4.2 version` prints it and the
Release for `v0.4.2` exists, and the fleet is cut from 0.4.2 before
`APPROVALD_ENFORCE=1` on Oct 11.

## SPEC.md at this release

The release PR does not edit `SPEC.md`; it carries `SPEC.md` as main holds it,
sha256 `3b1de87adf8ff2e3…`, the bytes 0.4.1 shipped. The amendments for this
release's behaviour are proposals in task notes, pending Carter's sign-off:

- APRV-499: §5.2 (the `tools` and `defaults.unmapped_tool` bullets, with the
  fix-round additions on attested bytes and on budgets and streaks), §7 (the
  `harness.tool.*` row) and §8 (`harness_tool` on a harness start). The §5.1
  canonical example is NOT amended in this release: it is pinned byte for byte
  to the scaffold fixture, so adding `unmapped_tool: record` there changes every
  scaffolded policy; that moves in a later pass with the scaffold. Text: the
  notes of `backlog/tasks/aprv-499 - ...`, sections "SPEC amendment PROPOSAL"
  and "Fix round 1", last two bullets.
- APRV-500: §5.2 (the `delegation` block is reserved) and §10.3
  (`verdict_source`, `model` reserved, the `model:` identity), with a §11.2
  note that no gate refusal code is added. Text: the notes of
  `backlog/tasks/aprv-500 - ...`, section "SPEC amendment PROPOSAL".

## Records only, not entries

APRV-501 is this release's own task. APRV-500's notes also carry a ruling for
the judge's stage 2 (the adviser): a judge is never delegable for
`policy.edit` and its sub-classes, `log.mutate`, `account.credential`,
`policy.core` or `harness.tool.unmapped`, and the grammar refuses those at
parse time before any delegation is honoured. It changes no code in this
release; in 0.4.2 every non-empty `delegation.classes` is already refused
`delegation-not-supported`.
