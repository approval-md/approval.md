# approval-md 0.4.8: release notes for downstream

The changelog section `## 0.4.8 — 2026-11-20` in [`CHANGELOG.md`](../../CHANGELOG.md)
is the authoritative list of changes. It becomes the GitHub Release body when
the tag is published (`scripts/release-notes.mjs`, APRV-396). This page is the
short companion for the downstream projects that pin this runtime. It covers
what 0.4.8 changes for a box operator and for a resident, and the order the
pins move in (APRV-534, APRV-535; #670).

Until the tag `v0.4.8` exists and the Trusted Publishing run has finished,
`approval-md@0.4.8` is only a version string this source tree carries. The tag
and its push are gated `release.publish` acts. Check the registry
(`npm view approval-md@0.4.8 version`) before baking the string anywhere.

## What a box operator gets

- **Cards go out during a held poll (APRV-534).** The listener `approval up`
  runs wakes its dispatch when the log changes (a file watcher, with a
  one-second stat fallback), so a new request's card is sent while the
  listener's `getUpdates` is still held. Under 0.4.7 a card waited for the
  poll to return, which is why the control plane's relay holds a box's poll
  for 4 s by default. Pacing, retries, and the payload, identity and
  authorization checks are 0.4.7's.
- **The poll body says so (APRV-535).** Against any `--api-base` other than
  the Bot API (the relay is one), each `getUpdates` body carries
  `"sends_during_poll": true`. The control plane's relay reads it and holds
  such a poll for `APPROVAL_RELAY_LONG_POLL_SENDS_DURING_POLL_S` when that is
  set; unset, every poll is held as before. `--no-sends-during-poll` on
  `approval up` leaves the field out. A request to `https://api.telegram.org`
  is byte for byte 0.4.7's.
- **`defaults.unclassified_command` (#670) is for the Claude Code hook only.**
  A resident box runs the Hermes hook, which keeps 0.4.7's deny whatever the
  key says, and the resident template does not carry the key. A core older
  than 0.4.8 refuses the key and fails the whole policy closed, so no
  template gains it while any box runs an older core.
- **Conformance.** `conformance/` is unchanged since 0.4.7.

## What changes for a resident

- **Approval cards arrive sooner.** A card no longer waits for the box's
  current poll to return. Its content, buttons and decisions are 0.4.7's.

## Upgrade order

1. Publish 0.4.8 and read it back:
   `npm view approval-md@0.4.8 version` and
   `npm view approval-md@0.4.8 dist.integrity`.
2. The control plane pins `APPROVAL_MD_VERSION=0.4.8` and the matching
   `APPROVAL_MD_INTEGRITY`, and its CI adds the `0.4.8` line to `CORE_PINS`
   (`test.yml` and `nightly.yml`, held equal by a test).
3. One canary box first, then the rest, one update per box.
4. A relay that should hold these boxes' polls longer sets
   `APPROVAL_RELAY_LONG_POLL_SENDS_DURING_POLL_S` after the boxes run 0.4.8.
   Nothing in this release requires it.
5. The checkpoint rebake and the re-mint `core` pin follow later; they are not
   on the critical path.

## SPEC.md

The release commit does not edit `SPEC.md` and proposes no new amendment.

sign-off stay as 0.4.7 left them.
