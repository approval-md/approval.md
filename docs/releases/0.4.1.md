# approval-md 0.4.1: release notes for downstream

The changelog section `## 0.4.1 — YYYY-MM-DD` in [`CHANGELOG.md`](../../CHANGELOG.md)
is the authoritative list of changes and becomes the GitHub Release body when
the tag is published (`scripts/release-notes.mjs`, APRV-396). This page is the
companion for the downstream projects that pin this runtime: what 0.4.1 changes
for a resident and for an operator, which pins move, the conformance versions,
and which `SPEC.md` hunks this release does not carry (APRV-476).

Until the tag `v0.4.1` exists and the Trusted Publishing run has finished,
`approval-md@0.4.1` is a version this source tree carries and nothing more. The
tag and its push are gated `release.publish` acts, so check the registry
(`npm view approval-md@0.4.1 version`) before baking the string anywhere.

Release-prep TODOs, delete before the PR opens: the two entries marked TODO in
the changelog (#616 APRV-489, #619 APRV-492) are in this page only as far as
their PRs have merged; the changelog date is a placeholder until the tag.

## What changes for a resident

- **Minimal approval cards (APRV-489, lands when #616 merges).** A policy that
  sets `channels.telegram.prompt.style: minimal` sends one short message: a
  plain-words headline, the payload's own words quoted, a deadline line, Approve
  and Deny, and the full technical card collapsed under "Full details". The
  default stays `technical`, byte for byte unchanged.
- **Supervised review you can finish (APRV-480..483, #614).** A review card
  shows the payload that ran, needs an explicit OK or Deny, and is held to the
  class's approvers roster. A held grade belongs to the account that tapped it.
  A doubled OK or Deny tap no longer loses the note prompt (APRV-492, lands when
  #619 merges), and a prompt that cannot be sent says so on the card.
- **No stuck cards behind a relay.** A tap on a card the listener is not holding
  is refused (APRV-456) and the live card stays armed; a card that cannot be
  offered for review is left for a terminal review instead of blocking the
  queue.

## What changes for an operator

- **Fail-closed on every harness.** A SIGTERM or SIGINT mid-wait withdraws the
  question and answers in the harness's own deny (APRV-473 Hermes, APRV-475 the
  other five); a signal while the spend waits on the log's lock blocks instead of
  being dropped (APRV-478); a signal while the runtime is loading gets the
  `hook-interrupted` directive from the bin (APRV-466). A grant that lands after
  the harness gave up starts nothing (`request-withdrawn`).
- **Relayed listener (APRV-456).** With `--api-base` naming anything but the Bot
  API, or `--no-stale-copy`, a tap on a nonce the listener does not hold is
  refused `nonce-not-issued`. Behavior change: after a restart, cards sent
  before it no longer decide behind a relay.
- **`APPROVALD_LISTEN=unix`.** TODO, owner to confirm the wording: the lead's
  brief says it is now proven; nothing in this repository names the variable,
  so the proof is in agentvillage-data or approval-md-hosted, not here. The
  `approval serve --listen unix:<path>` form shipped in 0.4.0.
- **Lock reclaim (APRV-479).** A writer that has waited out its lock timeout
  takes the lock back only from a holder that is provably gone in its own pid
  namespace and boot; an empty lockfile is taken after ten minutes, watched
  unchanged. A lock from another container, boot or host is never taken
  automatically: the `lock-timeout` message names the pid and the human-only
  `approval log unlock --pid <n|none>`, recorded as `audit.lock_reclaimed` with
  reason `operator-cleared` under the person's `human:` actor. Known gap
  (APRV-491, record only, #618): package-runner and script spellings of the CLI
  (`npx approval ...`, a script that calls it) escape the `policy.core`
  classification of human-only verbs, so `log unlock` is denied to an agent
  only as spelled `approval log unlock`.
- **Behavior changes to plan for.** A review needs the policy attested and an
  explicit `--ok` or `--deny` (scripts running a bare `approval audit review
  <seq>` must add `--ok`); a key declared by two tasks is refused; an empty
  lockfile left by an older version is taken after ten minutes.

Neither pin moves before `npm view approval-md@0.4.1 version` prints it and the
Release for `v0.4.1` exists, and the fleet is cut from 0.4.1 before
`APPROVALD_ENFORCE=1` on Oct 11.

**Roll every pin to 0.4.1 first.** The control-plane template keys
`channels.telegram.prompt.style: minimal` and `prompt.say` declarations are
refused by an older core, which fails the whole policy closed to all-`manual`.
Roll the template change only after every daemon reading the policy runs 0.4.1.
Also roll in this order for `audit.lock_reclaimed`: a follower on an older
schema reads a log that carries it as an unknown event type.
