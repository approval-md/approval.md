# Policy proposal, 2026-09-18 (second): sender identity and the read-scope line, one amend

Two lines combined so the human runs one `approval policy apply --pr`, one
amend and one policy pull request, the same way `policy-2026-09-18.md` combined
the ref-deletion and harness-launch lines. Each line's reasoning lives on its
own page and is not repeated here:

- `docs/proposals/sender-identity-2026-09.md` (APRV-324): a Telegram tap is
  attributed to the account the transport authenticated, and an account the
  policy does not name decides nothing.
- `docs/proposals/read-scope-2026-09.md` (APRV-347): a read that resolves
  outside this checkout, the scratchpad and the temp root is its own class. That
  page proposes `manual`; this page applies it at **`supervised-retro`**, the
  softer line the page itself names, on the operator's decision of 2026-09-18:
  the value of the class on this repository is the record (an agent reading
  the operator's Codex configuration and session transcripts to diagnose a
  probe, as happened that evening, should be visible in the retrospective
  sample), and a phone tap per out-of-scope read would have stalled that
  diagnosis six times. No `read_scope` block: the default roots stand, and the
  Seatbelt read jail for `approval run` and `approval sandbox` stays a separate
  decision. Raising the line to `manual` later is one edit.

**`<CARTER_TELEGRAM_USER_ID>` is a placeholder and MUST be replaced before this
page is applied.** It is the numeric `callback_query.from.id`, never a handle.
A wrong value maps the operator's own taps to nobody and refuses every phone
decision until the file is corrected from a terminal; the CLI channel keeps
working meanwhile. If the id is not known, apply this page with the placeholder
replaced by `0`, let one tap be refused, read the id off the
`audit.decision_refused` record (`payload.sender.id`), correct the value and
apply again with `--pr`, which updates the same open pull request.
