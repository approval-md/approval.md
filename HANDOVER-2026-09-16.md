## 4. Scoping the new harnesses: Hermes agent, Muse, Grok Bot, Instinct

Nothing in the repo mentions Hermes, Muse or Instinct today; Grok Bot has a
register entry and APRV-246. The register `docs/integrations-considered.md`
is the canonical place for scoping, one section per system with the existing
shape: What it is, What it exposes, Fit, Conclusion, Next steps. Research is
Opus or Sonnet subagent work, never Fable (CLAUDE.md model tiers), and a
register entry precedes any task.

The questions that decided fit for Claude Code, Cursor, Codex and Grok Build,
and will decide it again:

1. **Interception surface.** Is there a pre-execution hook with a deny
   verdict (Claude Code, Cursor, Grok Build shape), an MCP or tool-gateway
   path only (voluntary, agent can bypass), or nothing? Where is the hook
   configured, and can that file be committed and attested as a gate organ?
2. **Payload completeness.** Does the hook receive the command bytes, the
   per-call cwd, the tool name and input? Codex native v6 omitting the cwd is
   what blocks APRV-311; a hook that cannot bind the change cannot produce
   guard evidence.
3. **Failure mode.** Fail closed or fail open on timeout, crash, malformed
   output? Grok Build fails open with no setting; that shapes what may ever be
   activated.
4. **Identity and session.** A stable agent identity for `agent:<id>`, a
   session id for loop scope, and whether the harness can impersonate a human
   channel.
5. **Side-effect classes it reaches.** Shell, file writes, network, email,
   money. Which existing classifier and adapters apply, which are new.
6. **Demo shape.** What the smallest honest demo is (the Grok Bot connector
   runbook and `examples/web-agent-demo/runbook.md` are the patterns).

Suggested first move next session: one Opus research subagent per system
producing a draft register section against those six questions, with sources;
Fable reviews, Carter decides which get tasks. Grok Bot can start from its
existing entry and APRV-246's open rehearsal.

## 5. Working rules learned this week (also in the agent's memory)

- Never put `git checkout <branch>` in a runbook for the primary (see §2).
- After any records PR merges, the next `approval up` needs `log sync` first
  (until APRV-346).
- A shell command that names `SPEC.md` or `APPROVAL.md` classifies as a
  protected-path edit even when it is `git add` or `cp`; stage with
  `git commit -a` or `git add <dir>`, and read the policy via `sed -n`.
- The hook refuses heredocs, `for`/`while`, `node -e`, `awk`, `paste`,
  `git merge-base`, `git ls-tree`; PR bodies go through `--body-file`.
- Never `npm test | tail`; redirect to a log and grep `^ℹ (tests|pass|fail)`.
- Local Node 26 fails 22 email-adapter TLS tests ("ServerName to an IP
  address"); CI's Node 22 passes them.
- Sign-off is a granted edit (APRV-181): granted edits carry the plain suffix
  from birth; to ratify an unsampled one, daemon down, Edit-tool edit, Carter
  grants from `approval queue`, retry within the five-minute grace, then
  `approval log advance --pr` before the PR's guard runs.
- `gh pr merge <n> --merge` alone does not enqueue under the merge queue;
  `--merge --auto` does (CLAUDE.md rule 7 still says `--merge`).
- Opus lanes inherit the orchestrator's cwd; when the task lives in another
  worktree, tell them to `EnterWorktree` first.
